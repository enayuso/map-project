### Directions (Phase 4)

Tap **🧭 Directions** to open a Naver/Kakao-style route card (`src/routing/DirectionsSearchPanel.tsx`): two independently-tappable fields — "Choose starting point" (green dot) / "Choose destination" (red dot), each its own search box with typo-tolerant search, recent searches, and favorites, plus (origin only) a "📍 Use current location" shortcut. Either field can be set by search or by tapping a point on the map — a tap fills whichever field you last focused (highlighted with a light background), not always "origin first". A ⇅ button swaps the two, and picking a destination first (e.g. via a place card's "Directions" button) works too — origin is just whatever's still empty. Renders the route line, distance/duration, a ferry badge when relevant, and the turn-by-turn instruction list in a bottom sheet; a costing switcher (🚗/🚶/🚲) re-fetches the same trip with a different profile.

**Auto-fits the camera to the whole route (2026-09-10)** — every time a route successfully comes back (the first fetch, and any later refetch from switching 🚗/🚶/🚲, since a walking/biking path can trace a meaningfully different line than driving), the camera flies to fit the *entire* route geometry, not just the two endpoints: a straight line between origin and destination would badly clip a real road route, which regularly bows out around rivers/highway-only connections, so the fit bounds come from every coordinate along the decoded route polyline (`boundsFromRouteCoordinates` in `App.tsx`, feeding `Camera.fitBounds`).

**Route panel is now a real drag-to-expand bottom sheet (2026-09-10)**, matching Kakao/Naver's own — not the earlier fixed box capped at 55% of screen height. `RoutePanel.tsx` opens collapsed to just the essentials (costing switcher, distance/time, Start button, a small drag handle and "▲ Drag up for full directions" hint) and only reveals the full turn-by-turn list once you drag it open, snapping between two heights (a quick upward flick also snaps it open, same as a real bottom sheet) rather than requiring an awkward internal scroll through a tall fixed list. Built with core React Native (`Animated` + `PanResponder`, animating the sheet's actual height with `overflow: 'hidden'` clipping the turn list beneath it) rather than a third-party bottom-sheet library — no new native dependency/pod install needed for this.

This also fixed the auto-fit padding above, which undershot both edges at first (confirmed by your report — the route was rendering partly underneath the search panel and/or the route sheet, not fully visible in the gap between them). `DirectionsSearchPanel` and `RoutePanel` now each export their own real height as a constant (`PANEL_HEIGHT`/`PANEL_TOP`, `PEEK_HEIGHT`), and `App.tsx`'s fit padding is computed directly from those rather than independently guessed — so the two can't drift out of sync again the way the original guess did. The fit only needs to clear the sheet's collapsed (peek) height, not its dragged-open one, since padding around the fully expanded sheet would leave almost no map visible.

**Verified**: the bounds-computation logic was checked directly against a real Valhalla route (Belize City → San Ignacio, 2,505-point decoded polyline) outside the UI — the computed bounds' west/east/south/north matched the route's actual first/last coordinates and full extent exactly, not just plausibly. ### Zoomed-out UX cleanup, tiered place labels, and country border (Phase 4.5)

Zooming all the way out used to look broken, for two separate reasons — fixed together after a real screenshot surfaced the problem:

- **Label clutter**: every settlement's name (even tiny hamlets) rendered at every zoom level. `styles/basic.json` now has four tiered `place-labels-*` layers keyed to OSM's own `place` tag hierarchy (checked the real data first: only 4 places are tagged `city`, 16 `town`, 213 `village`) — cities show bold from zoom 0, towns from zoom 7, villages from zoom 10, everything else (hamlet/locality/suburb/neighbourhood/quarter) only from zoom 13. Standard cartographic label-prioritization, the same thing Kakao/Naver already do.
- **Hard edge at the sea layer's boundary**: the `sea` layer (see backend's `water_polygons` section) only has real data within roughly Belize's own extent — zoom out far enough and you'd hit a stark rectangular edge (this was the actual bug in the shared screenshot). We can't safely extend the sea polygon further without land data for Mexico/Guatemala/Honduras (it would render those countries as if underwater — a worse, more misleading error than a visible data boundary). Fixed by capping the zoom/pan range instead: `<Camera minZoom={9} maxZoom={19} maxBounds={[...]}>` in `App.tsx`. `minZoom` now applies to *pinch and double-tap* zoom too, not just the +/- buttons — a real MapLibre Native constraint, not custom touch logic. The exact value (9) is calibrated against the sea layer's real extent and this screen's aspect ratio, not guessed (see the comment above `MIN_ZOOM` in `App.tsx` for the math). `maxBounds` matches the sea layer's own extent and deliberately isn't shrunk any tighter — real towns we've tested (Corozal, Punta Gorda) sit near the country's extremes and need to stay reachable, even though that means a sliver of edge is still theoretically visible if you pan to one of those *and* stay fully zoomed out at the same time.
- **Bold country border**: a new `country-border` layer renders Belize's actual OSM-tagged national boundary (`boundary=administrative`, `admin_level=2` — confirmed present in our extract, including the border rivers Río Hondo and Sarstoon River) as a bold dashed maroon line, visually grounding "this is the country we cover" the way Kakao/Naver do.

**Verified**: style JSON confirmed valid and loading with zero `mbgl`/style-parse errors in the device log (checked directly). TypeScript/ESLint clean. Bold city labels and the new layers confirmed rendering via simulator screenshot. `minZoom`/`maxZoom`/`maxBounds` are native `<Camera>` props (confirmed against the library's real types), not custom logic — but the actual zoomed-out *feel* still needs your manual check in the real Simulator.app; this session's automated tap injection couldn't reliably drive repeated zoom-out taps to verify it live.

**Widened further (2026-09-13)**: you asked for zoomed-all-the-way-out to actually show the whole country, not just "as far as felt safe" — `MIN_ZOOM` was 9 specifically to stay inside the sea layer's data extent, a different, more conservative goal than "frame the whole country." Recomputed against `MAX_BOUNDS`' real extent (2.6° wide × 2.85° tall) and this screen's actual viewport-size-per-zoom-level (accounting for Mercator's latitude stretch at Belize's ~17°N): width is the binding constraint, and only zoom 7 fits it — zoom 8 still crops the east/west edges. `MapLibre`'s own `maxBounds` constrains the rendered viewport itself (not just the pan center), so lowering `MIN_ZOOM` further doesn't risk the "hard edge void" the original 9 was guarding against — MapLibre simply won't render past the box regardless. `MIN_ZOOM` is now **7**. **Blurriness fix (2026-09-11)**: you flagged that buildings/land looked badly blurry zoomed in on satellite view. Root cause is inherent to the imagery, not fixable for free: Sentinel-2's true-color band is ~10m/pixel native resolution, the satellite raster source's own `maxzoom` is 14 to match (`backend/martin-config.yaml`), and MapLibre upscales the same z14 tile for every zoom past that — by z19 that's the same pixel stretched ~32x linearly. Checked for a free, commercial-use-permitted, higher-resolution alternative before concluding there wasn't one: Planet's NICFI program does publish free ~4.77m imagery covering Belize, but its [license](https://assets.planet.com/docs/ToS_NICFI_User_level1.pdf) restricts use to conservation/forest-monitoring purposes, explicitly excluding ordinary commercial use — a dead end for this app, same as this project's other commercial-license constraints. Esri/Google/Bing satellite tiles are all under similar or stricter no-redistribution terms. Sub-meter imagery exists commercially (Maxar/Airbus/Planet's paid tiers) but isn't free, which is the whole reason Sentinel-2 was chosen in the first place (see `docs/PLAN.md`'s Locked Decision 3).

What *is* free: this app's own OSM building-footprint data, already sitting in the same `planet_osm_polygon` table the vector "basic" style already draws crisp buildings from — hybrid.json just never referenced it. Turns out that was the real problem, more than raw pixel resolution: hybrid.json had **no building layer at all**, so at high zoom individual buildings had literally nothing but soft photo texture to define their edges, while roads and labels (rendered as sharp vectors) stayed perfectly legible right next to them. Added a `buildings-outline` layer (`styles/hybrid.json`, synced to `src/styles/hybrid.json` as always) — a thin white stroke around each `has building` polygon from the existing `polygons`/`planet_osm_polygon` source (a source hybrid.json didn't have yet either), `minzoom: 14` to match the satellite source's own native-resolution ceiling. Doesn't (can't) sharpen the photo texture itself, but turns "an indistinguishable blur" into "clearly defined building footprints over a soft photo" — the same treatment real Kakao/Naver/Google hybrid views use for exactly this reason.

**Verified**: reproduced the reported blur first, in the simulator, zoomed into central Belize City with satellite on — confirmed genuinely bad (buildings were unreadable color smears). After the fix, same location, same zoom: every building now shows a crisp white outline; still-blurry photo texture visible only *inside* each footprint, not obscuring its shape. Martin restarted and confirmed serving the updated `/style/hybrid` with the new layer/source. Style JSON valid on both copies.

### Turn-by-turn live navigation (Phase 4.5)

Tap **▶ Start** on the route panel (after getting directions) to enter navigation mode: a top banner shows the upcoming turn (icon + instruction + live countdown distance), a bottom bar shows remaining distance/time and an **✕ End** button, and the search box/category bar/directions button hide themselves for a decluttered driving view. The camera switches to MapLibre Native's own follow mode (`<Camera trackUserLocation="course">`) — it centers and rotates to match your direction of travel automatically, a real native feature, not custom camera-chasing logic. The location dot's own heading arrow switches from compass-based (`mode="heading"`) to GPS-course-based (`mode="course"`) to match, since a phone's compass is noisy inside a moving vehicle.

**No map-matching** — `src/routing/navigation.ts` figures out "distance to the next turn" as a straight-line (haversine) distance from your live GPS fix to that maneuver's coordinate (which Valhalla gives us directly via `begin_shape_index` into the route's own decoded polyline — no separate lookup needed), advancing to the next maneuver once you're within 30m of it. This is a deliberate v1 simplification: good enough for a "turn in 300m" banner, not precise enough for real off-route detection or rerouting, neither of which this attempts. "Remaining distance/time" is similarly a sum of the not-yet-completed maneuvers' own lengths — it updates in discrete steps as each maneuver completes, not continuously along the road.

**Verified**: TypeScript/ESLint clean. The actual turn-advancement algorithm was validated against a real Valhalla route rather than assumed correct — fetched a live 10-maneuver route, decoded its polyline, and simulated "driving" it by stepping through the route's own real coordinates (which are genuine points on the road) through the exact same distance/threshold logic used in the app: it advanced through all 9 turns in the correct order with zero skips or double-advances, reaching the arrival maneuver exactly at the route's end. Every maneuver type code that route actually returned (start, left turn, roundabout enter/exit, keep-right, arrive) is mapped to a real icon in `MANEUVER_ICONS`, not falling through to the default arrow. App relaunches without crashing. The interactive flow itself — tap Directions, tap two points, tap Start, then watch it live-update while moving — is unusually deep (four+ chained taps before you can even observe anything) for this session's automated tap injection to drive reliably; it needs your manual test in the real Simulator.app more than most features here. One thing worth trying: the iOS Simulator can simulate a moving GPS track along real waypoints (`xcrun simctl location <udid> start --speed=<m/s> <lat1>,<lon1> <lat2>,<lon2> ...`) — feeding it the coordinates of an actual fetched route is a good way to watch the turn-by-turn banner update for real, once navigation mode is started.

### Fair meeting-point calculator (2026-09-10)

Tap **🤝 Meet Up** to add 2-5 people (search, "📍 Use current location", or a map tap — same input methods as Directions), then **Find a fair place to meet**. This is a real differentiator, not catch-up work: per [docs/research/09-kakao-naver-feature-audit.md](../docs/research/09-kakao-naver-feature-audit.md), **neither Kakao Map nor Naver Map actually has this as a native feature** — both punt to third-party apps built on their own APIs for it.

"Fair" means minimax, not average: `src/meetup/api.ts` pulls real restaurant/cafe/bar candidates near the group's centroid from the existing Typesense POI index, then sends every participant × every candidate through Valhalla's `/sources_to_targets` matrix endpoint in **one request** (not N×M individual `/route` calls) to get real road-network travel times, and ranks candidates by the *worst-off* participant's time — a venue where three people arrive in 4/4/25 minutes is not fair just because the average is decent, and a straight-line geometric midpoint would ignore the road network (and Belize's water/highway-only connections) entirely. A venue unreachable for even one participant is disqualified outright, not just penalized. Results show as colored per-participant time chips in a bottom sheet, best match first.

**Verified**: the full pipeline was run directly against real data outside the UI — three synthetic Belize City locations produced sensible, tightly-clustered top picks (3-4 minutes for everyone, real restaurant names) rather than a skewed or nonsensical ranking. TypeScript/ESLint clean, app relaunches without crashing.

### Live location sharing (2026-09-10)

Tap **📡** (above the satellite toggle) to either **share your own location** (generates a 6-character code, no account needed — see [sharing/README.md](../sharing/README.md) for the full access-model reasoning) or **view someone else's** by entering their code. A sharer's position pushes to the new `sharing/` backend service every 15s; a viewer polls every 10s and sees a distinct cyan marker update on the map. ### Fixed: recurring full-app freeze, and a Meet Up "double-fill" report (2026-09-11)

Two real, previously-unresolved bugs flagged during this session's earlier full QA pass, picked as the next priority once the audit follow-ups above were done. Both root-caused to the same bug.

**The freeze**: reproduced it directly rather than guessing — opened Directions, focused the origin field (opens its results dropdown), tapped "Use current location." The dropdown's own code path (`Keyboard.dismiss(); setShowResults(false);`) visibly ran (the device log confirmed the keyboard teardown actually fired, and location genuinely got enabled), yet the dropdown stayed on screen, unchanged, through three different follow-up taps — including one aimed at a completely blank area of the map, nowhere near any button. Since `src/search/SearchBox.tsx`'s results dropdown renders in a `<Modal transparent>` (needed to escape a real RN/MapView touch-swallowing bug — see below — but itself genuinely full-screen), a modal stuck in this state silently intercepts *every* tap anywhere on screen, not just its own field — exactly matching the original report's symptom of unrelated buttons (RoutePanel's tabs, the hazards button, DirectionsSearchPanel's own Cancel) all going unresponsive at once.

Root cause, confirmed against a real documented failure class rather than assumed: calling `Keyboard.dismiss()` synchronously in the same tick as the `setState` that hides a `<Modal>` races two independent native UIKit transitions (the modal's own dismiss animation and the keyboard's) against each other — see [facebook/react-native#8562](https://github.com/facebook/react-native/issues/8562), "Attempt to dismiss from view controller while a presentation or dismiss is in progress!". `SearchBox.tsx` had exactly this pattern in three places (selecting a result, tapping an extra shortcut, tapping the backdrop to dismiss).

**Fix**: a single `closeResults()` helper — hide the modal (`setShowResults(false)`) first, and defer `Keyboard.dismiss()` to the next tick (`setTimeout(Keyboard.dismiss, 0)`) so the two transitions never fire in the same pass. All three call sites now go through it.

**The Meet Up "double-fill" report**: `MeetupPanel` renders one embedded `SearchBox` per participant (2-5 at once) — the exact same component, so it was equally exposed to this same race. Tested the reported flow directly (fill Person 1 via "Use current location," then Person 2, repeated) after the fix: both fill correctly, dropdown closes and focus auto-advances every time, no duplication, "Find a fair place to meet" runs end-to-end to real results. No separate bug found — this is the same root cause, now fixed once in the one shared component both features use.

**Verified**: reproduced the exact freeze sequence, applied the fix, then repeated the identical sequence twice more — both times the dropdown now closes correctly, focus advances, and every other button on screen stays responsive throughout. Ran the full Meet Up flow (both participants via current-location, then "Find a fair place to meet") end-to-end with no anomaly. TypeScript/ESLint clean.

### App.tsx hook-extraction refactor (2026-09-13 – 2026-09-14)

The other half of the engineering audit's "App.tsx is 2,392 lines with 90+ `useState` calls" finding. Each self-contained feature's state and handlers are being pulled out into their own `src/<feature>/use<Feature>.ts` hook, mechanically, one feature at a time: write the hook (typed `Use<Feature>` interface + hook function), replace the old inline block in App.tsx with one `const feature = useFeature(...)` call, fix every remaining reference to the old raw identifiers, delete now-dead leftover functions, fix imports, confirm `tsc --noEmit`/`eslint` clean, and — every few hooks — relaunch in the Simulator and manually exercise the extracted feature with real data before moving on.

The recurring design split, in order of how much a feature touches core app state:
- **Utility panels with no cross-mode coupling** (error log, "More" menu, offline maps, weather, ferries, dive sites, border crossings, saved lists, live location sharing, road hazards, search-along-route): the hook owns everything — visibility, data, handlers — including its own `toggle`/`open`/`close`. `closeUtilityPanels` (relocated to right after `cameraRef`/`mapRef` so it's initialized wherever a hook needs it as a call-time constructor argument) and each panel's own toggle both just call into the hook.
- **Mutually-exclusive top-level modes** (the fair meeting-point calculator, the distance/area measurement tool — routing itself stays in App.tsx, see below): these hooks do *not* own their own toggle, since turning one on has to turn the other two (and routing) off. The hook exposes bare `activate()`/`reset()` (or `deactivate()`) primitives; App.tsx keeps a thin `toggleX` bridge function that calls those alongside the sibling toggles and core state (`closeCategoryBrowsing`, `selectedPlace`) the feature itself shouldn't need to know about.
- **Cross-feature bridges stay in App.tsx either way** — anything that reaches into core, widely-shared state (`selectedPlace`, `cameraRef`, routing's `destination`, `recordRecentSearch`) after a feature-specific action completes: picking a meetup candidate, a dive site's "get directions," a saved list's place, a search-along-route result, opening a POI correction sheet. The hook's job stops at "the user did this feature-specific thing"; what that means for the rest of the app is App.tsx's call.
- **Pure side-effect bridges** (iOS Spotlight indexing/selection, the Live Activity/Dynamic Island mirror): no owned state at all — every dependency is a parameter, since the entire feature *is* touching core state (favorites/recentSearches out to a native index and back; navigation state out to ActivityKit) rather than managing anything of its own.
- Core, deeply-coupled state deliberately left alone: routing/navigation state, "select on map," category browsing, favorites/recents, the basemap toggle, zoom control, location state — the legitimate architectural core the rest of these features hang off of.

All 16 candidate features have been extracted (`errors/useErrorLog`, `menu/useMoreMenu`, `offline/useOfflineMaps`, `weather/useWeather`, `ferries/useFerries`, `dive-sites/useDiveSites`, `border-crossings/useBorderCrossings`, `lists/useLists`, `sharing/useSharing`, `hazards/useHazards`, `meetup/useMeetup`, `measure/useMeasure`, `routing/useAlongRoute`, `spotlight/useSpotlight`, `routing/useLiveActivity`, `poi-corrections/usePOICorrection`), taking App.tsx from 2,392 lines / 90+ `useState` calls down to 1,714 / 26. What's left in App.tsx is the core described above, plus the cross-feature bridges themselves.

Two naming-collision bugs were self-caught by `tsc` (not user-reported) — naming a hook's returned instance the same as the old raw state variable it replaces (`const diveSites = useDiveSites(...)` colliding with the old `diveSites: DiveSite[]` array, same for `borderCrossings`) — fixed by renaming the array-shaped return field (`.sites`, `.crossings`, `.list`) so the instance name and its data aren't the same identifier. A third, different lint issue surfaced once `useSpotlight`'s effects moved out of App.tsx: `react-hooks/exhaustive-deps` had never fired on that exact effect *inside* App.tsx, because the linter can statically prove a `useState` setter or `useRef` object declared in the same component is stable — but once those same values arrive as a hook *parameter*, it's opaque to the linter and correctly asks for them in the deps array. Fixed for real (not suppressed): `recordRecentSearch` was wrapped in `useCallback` in App.tsx so its identity actually is stable, rather than disabling the rule.

### Shared modal coordinator (2026-09-14)

A follow-up to issue 10's fix, not a new bug: that fix hand-rolled a bespoke `hidingRoutePanel`/`onRoutePanelDismissed`/`onSheetDismissed` handoff for exactly one pair of Modals. An automated code-review pass over that fix pointed out the real risk this left in place — `grep '<Modal'` across `mobile/src` and `App.tsx` finds **12 components** each independently mounting a sibling `<Modal>` (`SearchBox`, `MeetupResultsSheet`, `ListViewSheet`, `PlaceCard`, `ReportCorrectionSheet`, `CategoryResultsSheet`, `RoutePanel`, `AlongRouteSheet`, `HazardInfoCard`, `FerryPanel`, `DiveSitesPanel`, `BorderCrossingInfoCard`), with mutual exclusion between them maintained by hand-grown, scattered boolean conditions at each render site (`!routingActive && !selectedPlace && !correction.target`, `routingActive ? null : selectedPlace`, etc.) rather than one mechanism — the exact shape of bug issue 10 fixed for one pair could recur for any other pair whose Modal doesn't happen to close in the same tick it displaces another.

**`src/modals/useModalCoordinator.ts`** generalizes the fix instead of leaving it pairwise. Each Modal-owning slot still reports the same `desired` boolean it always computed (`!!selectedPlace`, `showRoutePanel`, etc. — that part is unchanged); the coordinator decides which *one* desired slot is actually allowed to be visible, tracked as a request stack (most-recently-requested wins) and handed off through each Modal's own `onDismiss` (iOS-only; the same reliable "animation has actually finished" primitive issue 10 already established, not a guessed delay). A slot whose own `desired` is still `true` can be displaced by a more recently requested one and reappears automatically once the displacing slot closes and confirms dismissal — this is what makes `RoutePanel` reappearing after `AlongRouteSheet` closes (or `CategoryResultsSheet` reappearing after a `PlaceCard`/`ReportCorrectionSheet` detour closes) fall out of the general mechanism with no special-casing, rather than needing its own bespoke pair of flags the way `RoutePanel`/`AlongRouteSheet` did before this.

All 11 non-`SearchBox` Modal components were migrated to it (each gained an `onDismiss?: () => void` prop threaded to its own `<Modal>`; `PlaceCard`, `HazardInfoCard`, and `BorderCrossingInfoCard` additionally gained an explicit `visible` prop, since they'd previously derived it from their data prop being non-null — decoupling "do I have data" from "am I allowed to be presented" is exactly what lets a displaced card keep its data while hidden, ready to reappear). `useAlongRoute.ts` dropped back to a plain `wantsOpen`/`open()`/`close()` shape now that the coordinator owns the cross-Modal choreography — it no longer needs to know `RoutePanel` exists at all. `CategoryResultsSheet`'s and `PlaceCard`'s own `desired` expressions were also simplified, dropping the redundant `&& !selectedPlace && !correction.target` / equivalent cross-references now that the coordinator enforces exclusivity generally — confirmed safe to drop by tracing that a native-presented Modal (per issue 6) already blocks all touches to anything underneath it, so the scenario those extra conditions were guarding against (triggering one while another is genuinely on-screen) was never reachable through the UI to begin with.

`SearchBox.tsx` deliberately was **not** migrated in this first pass — its issue-9 bug is a same-tap race against its own backdrop, not a conflict with a second Modal, a different problem with its own existing, already-correct fix — but see the follow-up below, which migrates it too for a different reason (multiple simultaneous instances, not issue 9).

**Verified**: `src/modals/useModalCoordinator.test.tsx` unit-tests the state machine directly (promotion, displacement-without-premature-reveal, fallback-to-a-still-desired-displaced-slot, and an arbitrary multi-step sequence asserting at most one slot is ever visible at once) via a small `react-test-renderer` harness, since this project has no `@testing-library/react-hooks`. Writing that test caught a real bug before it ever reached the Simulator: the first version mutated the request stack in a plain `useRef`, which doesn't itself schedule a re-render — a displaced slot's `visible` stayed stuck `true` for one extra render because nothing prompted React to recompute it against the just-updated stack. Fixed by making the stack real `useState` instead, so updating it correctly triggers the re-render that recomputes who's on top. `tsc --noEmit`/`eslint` clean (project-wide, no errors — the one real lint hit, `react-hooks/exhaustive-deps` on the coordinator's own reconciliation effect, was fixed for real by adding the suggested deps rather than suppressed, since `desired` never has referential stability across renders anyway so the effect still runs every render exactly as intended). Live in the Simulator: re-confirmed the original `RoutePanel` ↔ `AlongRouteSheet` handoff in both directions through the new general mechanism; confirmed a three-deep chain (`CategoryResultsSheet` → `PlaceCard` → `ReportCorrectionSheet` → closing back out through `PlaceCard`'s absence straight to `CategoryResultsSheet` reappearing, then to a fully clean map) all correctly falls back through the stack with no special-casing; confirmed `HazardInfoCard` (report a hazard, tap its marker, confirm/remove) and `MeetupResultsSheet` → `PlaceCard` (pick a fair meeting point, select a result) both still work through the coordinator.

### Personal speedometer during navigation (2026-09-15)

Kakao/Naver both show a live speed reading during turn-by-turn navigation. ## Running it (iOS Simulator)

1. Backend must be running: `cd ../backend && docker compose up -d` (see [backend/README.md](../backend/README.md))
2. Install pods (first time, or after changing native deps):
   ```bash
   cd ios && bundle install && LANG=en_US.UTF-8 LC_ALL=en_US.UTF-8 bundle exec pod install
   ```
3. Start Metro: `npx react-native start`
4. Build for the simulator (see "Known issues" below for why plain `npx react-native run-ios` may not work as-is):
   ```bash
   xcodebuild -workspace ios/BelizeMap.xcworkspace -scheme BelizeMap -configuration Debug \
     -destination "platform=iOS Simulator,id=<SIMULATOR_UDID>" -derivedDataPath ios/build \
     CODE_SIGNING_ALLOWED=NO CODE_SIGNING_REQUIRED=NO CODE_SIGN_IDENTITY=""
   ```
5. Install & launch the built `.app` (`ios/build/Build/Products/Debug-iphonesimulator/BelizeMap.app`) on the simulator.

## Known issues hit getting this running (and their fixes)

These cost real time to track down — recorded so they don't get re-debugged from scratch:

1. **CocoaPods + non-ASCII project path**: `pod install` crashed with `Encoding::CompatibilityError` when the project lived under a Korean-named folder (지도). Ruby's `unicode_normalize` (used internally by CocoaPods for path handling) can't handle non-ASCII path components reliably, and a downstream `Pod::Executable.execute_command` subprocess call hit the same issue one level deeper (hermes-engine podspec). **Fix: keep the project path ASCII-only.** (This is why the project now lives at `MAP/map-project`, not the original `지도/map-project`.)

2. **Missing native MapLibre SDK — `'MapLibre/MapLibre.h' file not found`**: `@maplibre/maplibre-react-native` v11.x does **not** pull in the native MapLibre iOS SDK via CocoaPods — it injects it as a **Swift Package Manager** dependency from a `post_install` hook (`$MLRN.post_install(installer)`) that the library expects you to add to your own Podfile manually. It's not autolinked and isn't mentioned in the package's own README (only in the external docs site). **Fix**: added the following to `ios/Podfile`'s `post_install` block:
   ```ruby
   $MLRN.post_install(installer)
   ```

3. **Codesign failure — `resource fork, Finder information, or similar detritus not allowed`**: a currently-active, ecosystem-wide bug (affects Flutter too — see `flutter/flutter#180351`, `#181103`, `#189734`) where recent macOS versions tag files from "untrusted" sources (Homebrew, CocoaPods downloads, and apparently anything created by processes in this dev environment's lineage) with a kernel-enforced `com.apple.provenance` extended attribute that **cannot be stripped** by `xattr -d`/`-c` (it silently "succeeds" without actually removing it), and newer Xcode's codesign rejects bundles containing it. **Fix**: disable code signing for simulator builds — it isn't needed there anyway: `CODE_SIGNING_ALLOWED=NO CODE_SIGNING_REQUIRED=NO CODE_SIGN_IDENTITY=""`.

4. **Watchman hangs**: `watchman watch-project` hung indefinitely (0% CPU, not actually crawling) on this project, which made Metro appear stuck at "Waiting for Watchman". **Fix**: stopped and disabled the Watchman LaunchAgent (`launchctl unload -w ~/Library/LaunchAgents/com.github.facebook.watchman.plist`) — Metro falls back to Node's own file watcher without it, and the "Waiting for Watchman" log line turned out to be a harmless periodic retry message, not a hard blocker, once Watchman was out of the picture entirely.

5. **Camera not moving to the initial position — tiles requested at `0/0/0`**: `<Camera centerCoordinate={...} zoomLevel={...} />` silently did nothing (map sat at zoom 0 / world view). The library renamed these props: the current API is `<Camera initialViewState={{ center: [lng, lat], zoom }} />` (`center`/`zoom`, not `centerCoordinate`/`zoomLevel`). Since Metro doesn't type-check, the stale prop names were just silently dropped rather than raising a build error. Confirmed via `xcrun simctl spawn <udid> log show` showing tile requests for `.../planet_osm_line/0/0/0` instead of the expected zoom-13 tiles — that log-based check is the fastest way to diagnose "map renders but shows nothing/wrong area" in the simulator.

6. **Search results dropdown not receiving taps**: `src/search/SearchBox.tsx`'s results list, rendered as a plain absolutely-positioned `View` sibling after `</Map>` (the standard, documented pattern for overlaying UI on a map), never received touches — taps landed but `onPress` never fired, no matter the exact coordinates. This matches a known, unresolved React Native issue (`facebook/react-native#35612`): an absolutely-positioned RN overlay can have its touches swallowed by a native map view sibling underneath it, and no `pointerEvents` combination reliably fixes it. **Fix**: the results dropdown now renders inside a `<Modal transparent animationType="none">` — a genuinely separate native presentation layer, not just a z-index trick — which sidesteps the bug entirely. The search bar itself stays a plain overlay (unaffected by this issue); only the results list is wrapped in the Modal, and only while there's something to show, so the map stays fully interactive the rest of the time.

   **Confirmed working by hand.** Automated tap/text-injection through Claude Code's embedded simulator *panel* was unreliable enough (roughly 1-in-5 success, occasional spurious element-inspector triggers) that it couldn't be trusted as a test signal — turned out that panel is a lightweight preview, not a real interactive input surface (see issue 7 below). Opening the actual **Simulator.app** (`open -a Simulator`) and testing by hand confirmed the full flow works correctly: search → tap a result → camera flies to it → pin drops.

7. **Claude Code's embedded simulator panel is a preview, not a full input surface**: taps/typing sent through it (by both the automation tool *and* the user clicking the panel directly) were unreliable — inconsistent focus, dropped keystrokes, occasional accidental triggering of React Native's dev-mode element inspector. The `iosSimulator` capability was also seen flagged `"unsupported...disabled by its rollout flag"` in the desktop app's own feature-flag list, consistent with this being an early/rollout-gated integration rather than a full remote-control surface. **For any interaction-heavy testing, prefer the real Simulator.app** (`open -a Simulator`, or run from Xcode) over the embedded panel — its clicks/keystrokes go directly to the simulator with no intermediate layer, and behave like a real device.

8. **This dev machine is memory-constrained (8GB total) for this stack**: Xcode + iOS Simulator + Docker (Postgres/Nominatim/Typesense/Martin) + Metro + Claude Code running together can push free RAM to near zero and force active swapping (confirmed via `vm_stat`/`sysctl vm.swapusage` — as low as ~60MB free, 2.4GB in swap, mid-session). This shows up as sluggishness, dropped input, and occasional Simulator crash/reboot — not application bugs. If things feel unresponsive, check `memory_pressure` and close other apps (a browser, Spotify, editors) before assuming something's broken. Colima's Docker VM was tuned down from 4GB (needed transiently for the Nominatim import) to 3GB for ongoing use — see [geocoding/README.md](../geocoding/README.md).

   **Recurrence, worth recognizing quickly next time (2026-09-10)**: hit the extreme end of this — the app rendered fine but was completely unresponsive to any tap (not just one feature; everything). The tell was in Metro's own log, not the app: it was looping the same `[timeout] connection terminated with Device... after not responding for 60 seconds` error over and over, meaning Metro itself couldn't hold a connection to the device, not just "the app is slow." Free RAM was down to ~60MB with ~4GB in swap at the time. Restarting Metro and relaunching the app did *not* fix it on their own (as expected — the bottleneck was available memory, not process state); closing a couple of other heavy apps (browser, Discord) to free RAM did. **If Metro's log shows repeated connection timeouts and the app ignores every tap, check `memory_pressure` before debugging app code** — it's very unlikely to be a new regression.

9. **Search bar dropdown opens then instantly closes**: reported as "whenever i click on it, it just opens but immediately closes." Root cause is a different bug from issue 6's touch-swallowing — this one is a genuine timing race, not a touch-routing problem. `SearchBox.tsx`'s results dropdown is a `<Modal>` (needed per issue 6) that mounted **synchronously** inside the `TextInput`'s `onFocus` handler. That means the exact same physical tap that focuses the input can also land on the Modal's now-present full-screen backdrop the instant it appears — the touch-*up* of that one gesture gets delivered to whatever is topmost at that screen point at that moment, which is now the backdrop, whose `onPress` dismisses the dropdown. Net effect: the dropdown opens and is closed again by the same tap, visible as an instant flicker or nothing at all. This had likely been present since the dropdown was first built (issue 6), but only became reliably noticeable once there was actual content — favorites/recents — for it to show on focus with an empty query; before that it may have opened onto a genuinely empty list and looked the same as "did nothing," masking the flicker.

   **Fix, two layers**: (1) `onFocus` no longer sets `showResults` directly — it schedules that update via `setTimeout(fn, 50)` instead, so the Modal only mounts *after* the opening tap's touch-up has already been fully processed, leaving no in-flight touch to bleed onto the backdrop. (Would have used `InteractionManager.runAfterInteractions` for this — it's the API React Native had for exactly this purpose — but confirmed directly in `node_modules/react-native/index.js` that it's been **removed from RN core** as of this project's RN version, throwing `'InteractionManager has been removed from react-native core... use requestIdleCallback instead'` if touched; used `setTimeout` instead.) (2) as a second, independent layer, the backdrop's `dismiss()` now ignores any dismiss request that arrives within 300ms of the dropdown having opened (`openedAtRef`), so even if a stray touch does bleed through, it's ignored rather than trusted.

   **Verified**: TypeScript/ESLint both clean. Interactive confirmation blocked by issue 7's tap-injection unreliability (several fresh attempts through the embedded panel this session registered no focus at all — no keyboard, no cursor, screen pixel-identical before/after each tap — consistent with that known ~1-in-5 success rate, not evidence against the fix). Needs your manual check in the real Simulator.app.

   **Recent search history display** (asked about alongside this bug): unaffected by the above — it's plumbed entirely separately, through `src/places/favorites.ts` (AsyncStorage-backed `getRecentSearches`/`addRecentSearch`, deduped by id, most-recent-first, capped at 8) and wired into three selection points in `App.tsx` (search selection, category-browsing selection, map-tap POI selection), all confirmed correct by direct code read, not changed by this fix. Display-side, `SearchBox.tsx` shows it whenever the query is under 2 characters and there's at least one favorite or recent search: a "⭐ Saved places" section (if any favorites exist) followed by a "🕐 Recent" section (if any recent searches exist), each just a plain list of name/subtitle rows reusing the same row styling as live search results. This section almost certainly hasn't been visibly reachable until now, since the same open-then-close race in this issue was firing on every focus — which is likely the real reason it looked broken enough to ask about.

10. **`RoutePanel`'s "🔍 search along route" button didn't open `AlongRouteSheet`**: found during the App.tsx hook-extraction refactor's live-simulator verification. First diagnosis (recorded in this file's refactor section, and worth leaving visible as a correction rather than quietly editing away) assumed this was issue 9's exact bug pattern again — a Modal mounted synchronously inside a tap handler, same tap's touch-up bleeding onto its own backdrop. That was **wrong**, caught only by actually fixing it that way and testing live rather than trusting the pattern-match: applying issue 9's two-layer fix to `useAlongRoute.ts`'s `open()`/`close()` changed nothing. Confirmed the real cause directly — a debug `<Text>` rendered straight off `alongRoute.visible` (bypassing `AlongRouteSheet`'s own `<Modal>` entirely) proved the state genuinely was flipping to `true`; the native (`xcrun simctl spawn booted log show`) console then showed the actual failure: `Attempt to present <RCTFabricModalHostViewController> ... which is already presenting <RCTFabricModalHostViewController>`. `RoutePanel` itself is a `<Modal>` (per issue 6, to escape the same MapView-swallows-touches bug), and it's already presented the entire time `AlongRouteSheet` is reachable (its search icon lives inside that Modal) — two `<Modal>`s can't both be presented at once from the same presenting view controller, so iOS silently drops the second `present()` call rather than stacking it.

    **Fix**: treat the two Modals as mutually exclusive, handed off via each one's `onDismiss` (iOS-only; fires once the dismiss *animation* has actually finished, not just when `visible` flips — the reliable primitive here instead of guessing at a delay long enough for a `animationType="slide"` transition). `useAlongRoute.ts`'s `open()` doesn't set `visible` directly; it sets `hidingRoutePanel`, which `App.tsx` ANDs into `RoutePanel`'s own `visible` prop. Only once `RoutePanel`'s Modal reports back via its `onDismiss` (wired to the hook's `onRoutePanelDismissed`) does `visible` actually become `true`, so `AlongRouteSheet`'s Modal only ever tries to present once `RoutePanel`'s has genuinely finished clearing the way. `close()` is the mirror image: hide `AlongRouteSheet`'s own Modal first, and only restore `RoutePanel` (clearing `hidingRoutePanel`, via `AlongRouteSheet`'s own new `onDismiss` → the hook's `onSheetDismissed`) once that confirms it's fully gone too.

    **Verified**: `tsc --noEmit`/`eslint` clean, full Jest suite passing. Live in the Simulator: opened Directions, got a route, tapped 🔍 — `AlongRouteSheet` now genuinely appears (previously nothing happened, confirmed both before and after the wrong fix attempt); selected "Food," got real along-route results with distance-ahead/off-route metrics; tapped a result, and `RoutePanel` correctly reappeared afterward with the new destination and a refetched route — confirming the handoff works cleanly in both directions, not just the one that was originally broken.

11. **A `SearchBox` extraShortcut that itself opens native UI can silently fail to appear**: found building the Meet Up "Use a shared location" action (see its own section above). `handleExtraShortcut` in `src/search/SearchBox.tsx` closes this dropdown's own `<Modal>` (`closeResults()`) and then calls the shortcut's `onPress` in the very same tick — fine for every shortcut that existed before this (current-location, select-on-map both just touch JS state), but a shortcut whose action presents *another* native UI (here, `Alert.prompt`) raced against this dropdown Modal's own not-yet-complete dismissal and reliably lost — the alert never appeared, confirmed repeatedly with a freshly-reset Metro bundle each time to rule out a stale-bundle artifact rather than a real race. Neither a plain deferred `setTimeout` nor chaining off the dropdown's own `onDismiss` (the fix issue 10 above used, for two `<Modal>`s) fixed it — the latter made things *worse*, a real `Cannot read property 'getSnapshot' of null` crash from touching `useSyncExternalStore`-backed state inside a native bridge callback frame.

    **Root-caused before settling on a fix, not just patched at the first thing that seemed to help**: built a throwaway diagnostic (a temporary More-menu item calling `Alert.prompt` directly, and a temporary hijack of an existing `MeetupPanel` button to do the same) to isolate exactly where the failure lived. Result: `Alert`/`Alert.prompt` work correctly everywhere tried — a bare `Pressable` in the More menu, and a bare `Pressable` inside this exact `MeetupPanel` with an active session and participants already filled — except specifically through the `SearchBox`-dropdown-closing chain. That pointed at the mechanism (presenting new native UI from within a `SearchBox` dropdown's own close sequence), not a timing constant needing tuning.
