# mobile (BelizeMap)

React Native app (0.87.1) + `@maplibre/maplibre-react-native` (11.3.10), rendering the same [PostGIS + Martin backend](../backend/) and [style](../styles/basic.json) already proven out in [web-preview/](../web-preview/). Also wires up search ([search/](../search/) + [geocoding/](../geocoding/), see `src/search/`) and turn-by-turn directions ([routing/](../routing/), see `src/routing/`). See [docs/PLAN.md](../docs/PLAN.md) for phase context.

### Directions (Phase 4)

Tap **🧭 Directions**, then either tap two points on the map or use the search box to set a start and end point (first pick = origin, second = destination — searching while a place is already pinned uses it as the destination immediately, the "search then get directions to it" flow). Renders the route line, distance/duration, a ferry badge when relevant, and the turn-by-turn instruction list in a bottom sheet; a costing switcher (🚗/🚶/🚲) re-fetches the same trip with a different profile.

**Verified**: the client-side polyline decoding + Valhalla response parsing (`src/routing/api.ts`) was checked directly against a real `/route` response outside the UI — the first decoded coordinate matched the query's origin exactly, the last matched the destination, and all 65 points along the route fell inside Belize's bounding box. The UI wiring itself (button → map taps → route line + panel) renders without crashing, but — per issue 7 below — needs a manual tap-through in the real Simulator.app to fully confirm, the same way Phase 2's search box did.

### Whole-country coverage, location, and compass (Phase 4.5)

- **Coverage**: the app isn't actually limited to the two pilot areas — all backend services were built from the full Belize OSM extract, confirmed working for Belmopan, Corozal, and Punta Gorda too. See [docs/PLAN.md](../docs/PLAN.md) Phase 4.5.
- **Current location**: tap 📍 (bottom-right) to center the map on the device's current position — uses MapLibre Native's built-in `useCurrentPosition`/`<NativeUserLocation>`, no extra geolocation package. Location tracking only starts on first tap, so the permission prompt doesn't fire before it's needed. On the Simulator, set a fake GPS location first: `xcrun simctl location <udid> set <lat>,<lon>` (the Simulator has no real GPS).
- **Compass**: built into MapLibre Native (`compass`, `compassHiddenFacingNorth`, `compassPosition` props on `<Map>`) — appears only when the map is rotated, hides at north, and resets bearing on tap, all native behavior with zero custom code. Confirmed the hide-at-north behavior works (no compass visible at the default view).

### Place cards + tap-to-query POIs (Phase 4.5)

Tap any place — a search result, or a POI dot rendered directly on the map — to get a bottom-sheet card (`src/places/PlaceCard.tsx`) with its name/category, a live travel-time preview from your current position (via the same Valhalla `fetchRoute` routing uses), and Directions/Close buttons. Map-tap hit-testing uses MapLibre Native's built-in `mapRef.current.queryRenderedFeatures(point, {layers: ['poi-circles']})` against the new `poi-circles` layer in `src/styles/basic.json` (businesses/amenities/tourism points, zoom 15+) — previously the style only rendered settlement/neighborhood labels, nothing individually tappable. Search results and map-tapped POIs both normalize to the same `SearchResult` shape, so one card component handles both. Tapping "Directions" on a card feeds it straight into the existing routing flow as the destination.

**Verified**: TypeScript compiles clean against the real `@maplibre/maplibre-react-native` type definitions (checked `MapRef.queryRenderedFeatures` and `PressEvent.point` directly in the library's `.d.ts` rather than assuming the shape). App relaunches and renders without crashing — pure JS + style-JSON change, no native rebuild needed. Interactive tap-through still needs a manual pass in the real Simulator.app, per issue 7 below — this session's own attempt at automated verification hit issue 7 again (see there).

### Category quick-filter browsing (Phase 4.5)

A horizontal chip bar (`src/categories/CategoryBar.tsx`) sits under the search box — 🍽 Food, ☕ Cafes, 🛒 Grocery, ⛽ Gas, 🏧 Bank/ATM, 💊 Pharmacy, 🏨 Hotels, 🎡 Attractions, 🍺 Bars, 🏥 Health (scroll for more). Tapping one calls `searchNearby()` (`src/search/api.ts`) against Typesense with a geo-radius filter centered on wherever the map is currently showing (not the device's GPS position — deliberately, since you're often browsing an area you aren't standing in, matching Kakao/Naver's own "search this area" behavior), sorted nearest-first. Results render two ways at once: as `<Marker onPress>` pins directly on the map (a native annotation, so — unlike an RN overlay — it isn't subject to issue 6's touch-swallowing bug at all) and as a distance-labeled list in `src/categories/CategoryResultsSheet.tsx` (Modal-based, same reasoning as `SearchBox`'s dropdown, since this list mounts/unmounts with state). Tapping either a pin or a list row opens the same `PlaceCard` used everywhere else.

The chip bar itself (`CategoryBar.tsx`) is a plain absolutely-positioned overlay, *not* wrapped in a Modal — it's a static, always-mounted set of `Pressable`s, the same shape as the already-confirmed-working "🧭 Directions" button, not a dynamically-appearing list like the thing issue 6 actually affected.

**Verified**: the exact Typesense query (`filter_by=category:=X && location:(lat,lon,8 km)`, `sort_by=location(lat,lon):asc`) was run directly against the live backend outside the app and confirmed correct — 53 restaurants within 8km of Belize City, correctly sorted by `geo_distance_meters`. TypeScript and ESLint both clean. App relaunches without crashing and the chip bar renders correctly. Automated tap-through on an actual chip did not register at all this attempt (confirmed via Typesense's own request logs showing nothing arrived) — a milder version of issue 7's unreliability rather than a code defect, since the query itself is independently verified working. Needs the same manual real-Simulator.app pass as everything else in this list.

### Zoom control (Phase 4.5)

A stacked +/− pill button on the right edge, above the 📍 locate button — same placement and shape as Kakao/Naver's own zoom control. Each tap calls `cameraRef.current.zoomTo(zoom ± 1, { duration: 250 })` (a real `CameraRef` method, confirmed against `@maplibre/maplibre-react-native`'s own `.d.ts` rather than assumed); the live zoom level is tracked via the `<Map onRegionDidChange>` event (also confirmed against the library's types: `ViewStateChangeEvent.zoom`), so the buttons grey themselves out at the configured bounds (zoom 9-19, see the next section for why 9 not something lower) and stay in sync with pinch-zooms, double-tap-zooms, and every other camera move in the app (search selection, category browsing, locate-me), not just their own taps. Pinch-to-zoom and double-tap-zoom keep working as before — MapLibre's own defaults, untouched — this is the explicit-button alternative both Kakao and Naver offer alongside gestures, not a replacement for them.

**Verified**: TypeScript/ESLint clean, app relaunches without crashing, button renders in the correct position with the right visual state. Automated tap-through didn't produce a visible zoom change on this attempt — the same input-reliability limitation as issue 7/the category-bar note above, not a code defect (the underlying API calls are confirmed real and correctly typed). Needs a manual real-Simulator.app check.

### Zoomed-out UX cleanup, tiered place labels, and country border (Phase 4.5)

Zooming all the way out used to look broken, for two separate reasons — fixed together after a real screenshot surfaced the problem:

- **Label clutter**: every settlement's name (even tiny hamlets) rendered at every zoom level. `styles/basic.json` now has four tiered `place-labels-*` layers keyed to OSM's own `place` tag hierarchy (checked the real data first: only 4 places are tagged `city`, 16 `town`, 213 `village`) — cities show bold from zoom 0, towns from zoom 7, villages from zoom 10, everything else (hamlet/locality/suburb/neighbourhood/quarter) only from zoom 13. Standard cartographic label-prioritization, the same thing Kakao/Naver already do.
- **Hard edge at the sea layer's boundary**: the `sea` layer (see backend's `water_polygons` section) only has real data within roughly Belize's own extent — zoom out far enough and you'd hit a stark rectangular edge (this was the actual bug in the shared screenshot). We can't safely extend the sea polygon further without land data for Mexico/Guatemala/Honduras (it would render those countries as if underwater — a worse, more misleading error than a visible data boundary). Fixed by capping the zoom/pan range instead: `<Camera minZoom={9} maxZoom={19} maxBounds={[...]}>` in `App.tsx`. `minZoom` now applies to *pinch and double-tap* zoom too, not just the +/- buttons — a real MapLibre Native constraint, not custom touch logic. The exact value (9) is calibrated against the sea layer's real extent and this screen's aspect ratio, not guessed (see the comment above `MIN_ZOOM` in `App.tsx` for the math). `maxBounds` matches the sea layer's own extent and deliberately isn't shrunk any tighter — real towns we've tested (Corozal, Punta Gorda) sit near the country's extremes and need to stay reachable, even though that means a sliver of edge is still theoretically visible if you pan to one of those *and* stay fully zoomed out at the same time.
- **Bold country border**: a new `country-border` layer renders Belize's actual OSM-tagged national boundary (`boundary=administrative`, `admin_level=2` — confirmed present in our extract, including the border rivers Río Hondo and Sarstoon River) as a bold dashed maroon line, visually grounding "this is the country we cover" the way Kakao/Naver do.

**Verified**: style JSON confirmed valid and loading with zero `mbgl`/style-parse errors in the device log (checked directly). TypeScript/ESLint clean. Bold city labels and the new layers confirmed rendering via simulator screenshot. `minZoom`/`maxZoom`/`maxBounds` are native `<Camera>` props (confirmed against the library's real types), not custom logic — but the actual zoomed-out *feel* still needs your manual check in the real Simulator.app; this session's automated tap injection couldn't reliably drive repeated zoom-out taps to verify it live.

### Favorites + recent searches (Phase 4.5)

A ★ button on `PlaceCard` saves/unsaves the current place. `SearchBox`, when focused with an empty query, shows "⭐ Saved places" and "🕐 Recent" sections instead of an empty dropdown — the same pre-typing shortcut Kakao/Naver show. Persisted locally via `@react-native-async-storage/async-storage` (`src/places/favorites.ts`) — the **first new native dependency since MapLibre itself**, so this one needed a real rebuild (`pod install` + `xcodebuild`), not just a Metro reload. `App.tsx` owns the `favorites`/`recentSearches` state (loaded once on mount from storage) so `SearchBox` and `PlaceCard` can't disagree about it. Any place selection — typed search, a category-chip result, or a direct map-POI tap — records a "recent," matching how Kakao/Naver's own recents track anything you've looked at, not just typed queries.

Also fixed one existing behavior that would have undercut this: `SearchBox` used to leave the selected place's name sitting in its own text field after a selection, so the box was rarely genuinely empty again — meaning the new shortcut list would rarely get a chance to show. It now clears back to empty on selection instead (the place shows on the map/its card, not duplicated in the search bar).

**Verified**: TypeScript/ESLint clean. The native module's own storage directory (`RCTAsyncLocalStorage_V1`) shows up in the device log after the rebuild with zero errors — direct evidence it's actually initializing and persisting, not just failing silently. App relaunches and renders correctly post-rebuild. The save/tap-through itself still needs a manual real-Simulator.app check, per issue 7 below.

### Satellite/hybrid basemap toggle (Phase 4.5)

A 🛰️/🗺️ button (above the zoom control) swaps the entire map style between the normal vector map and a new "hybrid" style — Sentinel-2 satellite imagery with roads, the country border, and place labels layered on top in colors chosen to stay legible over photographic imagery, the same idea as Kakao's 스카이뷰/Naver's satellite view. It's a full `mapStyle` swap (`basicStyle` ↔ `hybridStyle`, both bundled JSON, see `src/styles/hybrid.json`), not per-layer visibility toggling — simpler, and MapLibre Native keeps the camera position across the swap on its own.

The imagery itself is a real, from-scratch data pipeline — see [backend/README.md](../backend/README.md)'s `satellite` section and `scripts/build_satellite_mosaic.sh` for the full story (free Sentinel-2 data sourcing, mosaicking ~20 tiles, baking an MBTiles pyramid, serving it through Martin). Only the client side lives here: `App.tsx`'s `showSatellite` state and the toggle button.

**Verified**: TypeScript/ESLint clean. Martin confirmed serving real satellite tile content — fetched and visually decoded tiles over both Belize City and the Ambergris Caye reef directly, not just checked for a 200 status. Style JSON valid, app relaunches without crashing, toggle button renders in the right spot. A "hooks order" warning briefly seen in the device log during this work was confirmed to belong to a stale process from an earlier hot-reload mid-edit, not the current build (checked by filtering the log to the running process's own PID — zero errors there). The actual tap-to-toggle switch still needs a manual real-Simulator.app check, per issue 7 below.

### Turn-by-turn live navigation (Phase 4.5)

Tap **▶ Start** on the route panel (after getting directions) to enter navigation mode: a top banner shows the upcoming turn (icon + instruction + live countdown distance), a bottom bar shows remaining distance/time and an **✕ End** button, and the search box/category bar/directions button hide themselves for a decluttered driving view. The camera switches to MapLibre Native's own follow mode (`<Camera trackUserLocation="course">`) — it centers and rotates to match your direction of travel automatically, a real native feature, not custom camera-chasing logic. The location dot's own heading arrow switches from compass-based (`mode="heading"`) to GPS-course-based (`mode="course"`) to match, since a phone's compass is noisy inside a moving vehicle.

**No map-matching** — `src/routing/navigation.ts` figures out "distance to the next turn" as a straight-line (haversine) distance from your live GPS fix to that maneuver's coordinate (which Valhalla gives us directly via `begin_shape_index` into the route's own decoded polyline — no separate lookup needed), advancing to the next maneuver once you're within 30m of it. This is a deliberate v1 simplification: good enough for a "turn in 300m" banner, not precise enough for real off-route detection or rerouting, neither of which this attempts. "Remaining distance/time" is similarly a sum of the not-yet-completed maneuvers' own lengths — it updates in discrete steps as each maneuver completes, not continuously along the road.

**Verified**: TypeScript/ESLint clean. The actual turn-advancement algorithm was validated against a real Valhalla route rather than assumed correct — fetched a live 10-maneuver route, decoded its polyline, and simulated "driving" it by stepping through the route's own real coordinates (which are genuine points on the road) through the exact same distance/threshold logic used in the app: it advanced through all 9 turns in the correct order with zero skips or double-advances, reaching the arrival maneuver exactly at the route's end. Every maneuver type code that route actually returned (start, left turn, roundabout enter/exit, keep-right, arrive) is mapped to a real icon in `MANEUVER_ICONS`, not falling through to the default arrow. App relaunches without crashing. The interactive flow itself — tap Directions, tap two points, tap Start, then watch it live-update while moving — is unusually deep (four+ chained taps before you can even observe anything) for this session's automated tap injection to drive reliably; it needs your manual test in the real Simulator.app more than most features here. One thing worth trying: the iOS Simulator can simulate a moving GPS track along real waypoints (`xcrun simctl location <udid> start --speed=<m/s> <lat1>,<lon1> <lat2>,<lon2> ...`) — feeding it the coordinates of an actual fetched route is a good way to watch the turn-by-turn banner update for real, once navigation mode is started.

### Data-source attribution (Phase 4.5)

A small, always-visible, tappable footer at the bottom of the map (`src/attribution/AttributionFooter.tsx`) — "© OpenStreetMap contributors" always (every OSM-derived layer: roads, buildings, place names, POIs, the sea polygon), plus a Copernicus/Sentinel credit whenever the satellite/hybrid basemap is showing. Both open their respective copyright/terms page via `Linking.openURL`. This isn't optional polish — OSM's ODbL and Copernicus's Sentinel data terms both require visible attribution wherever the data is displayed, and this is a commercial-venture app (`docs/PLAN.md` Locked Decision 4), so it needed to actually exist, not just be a noted-for-later item.

**Deliberately not MapLibre Native's own built-in attribution button** (`<Map attribution>`, explicitly set to `false`): that control parses HTML anchor tags out of each style source's `attribution` string on the native side, and MapLibre Native's own issue tracker documents this as having caused real crashes on iOS — confirmed by checking their GitHub issues first, not assumed. A plain RN component with `Linking` gets the identical compliance outcome (OSMF's Attribution Guidelines call a "suitably clear and prominent link" from the map view sufficient) without depending on that native parser at all.

**Verified**: TypeScript/ESLint clean, confirmed rendering correctly via simulator screenshot — visible, legible, underlined to signal it's a link, positioned clear of the MapLibre logo and other controls.

### Field data collection — Add/Edit Place (Phase 3 Track B)

A dark "＋" button (bottom-left, clear of the MapLibre logo and hidden mid-routing/navigation) opens `src/places/AddEditPlaceModal.tsx` — a quick form (name, category, phone, hours, website, an informal/landmark address field) that creates a new place at the current map center via `src/places/placesApi.ts`, which talks to the PostgREST write API on `http://127.0.0.1:3001` (see `backend/README.md`'s `places` section). New places are created `verification_status='field_verified'` — you're standing there confirming it, so it starts more trusted than a bulk OSM import.

**Editing** works the same way from an existing place's card — a "✎" button next to the ★ favorite button, but **only when the place is reliably one of ours to edit**: `placesApi.ts`'s `placeIdFromSearchResultId()` recovers the real `places.id` UUID from a search/category-browsing result's id (Typesense's own document id *is* `places.id` as of Phase 3 Track B), and the edit button is simply omitted — not shown disabled — for anything that isn't backed by a confirmed `places` row: a Nominatim address result, or a POI tapped directly on the map (sourced from the raw vector tile, not guaranteed to have a matching `places` row — e.g. unnamed POIs render as dots but were never seeded, since seeding requires a name). Editing those is a deliberate v1 gap, not an oversight.

**What "saved" means right now**: writes go straight to the canonical `places` table and are real/durable immediately. They do *not* appear in search/category-browsing results until the next `scripts/reindex_pois.sh` run, since Typesense is a periodically-rebuilt cache, not a live view — expected behavior for this phase, not a bug (see `backend/README.md`).

**Verified**: TypeScript/ESLint clean, app relaunches without crashing, button renders in the correct position (moved once already, to clear the MapLibre logo it initially overlapped). The write path itself was verified directly against the real PostgREST API, independent of the UI — a full create → read → update → delete round trip via `curl`, confirming records persist correctly and `updated_at` advances on edit (the schema's trigger, not app code, keeps that accurate). The actual tap-through — pressing "＋", filling in the form, saving — still needs your manual check in the real Simulator.app, per issue 7 below.

## Running it (iOS Simulator)

1. Backend must be running: `cd ../backend && docker compose up -d` (see [backend/README.md](../backend/README.md))
2. Install pods (first time, or after changing native deps):
   ```bash
   cd ios && bundle install && LANG=en_US.UTF-8 LC_ALL=en_US.UTF-8 bundle exec pod install
   ```
3. Start Metro: `npx react-native start`
4. Build for the simulator (see "Known issues" below for why plain `npx react-native run-ios` may not work as-is):
   ```bash
   xcodebuild -workspace ios/BelizeMap.xcworkspace -scheme BelizeMap -configuration Debug \
     -destination "platform=iOS Simulator,id=<SIMULATOR_UDID>" -derivedDataPath ios/build \
     CODE_SIGNING_ALLOWED=NO CODE_SIGNING_REQUIRED=NO CODE_SIGN_IDENTITY=""
   ```
5. Install & launch the built `.app` (`ios/build/Build/Products/Debug-iphonesimulator/BelizeMap.app`) on the simulator.

## Known issues hit getting this running (and their fixes)

These cost real time to track down — recorded so they don't get re-debugged from scratch:

1. **CocoaPods + non-ASCII project path**: `pod install` crashed with `Encoding::CompatibilityError` when the project lived under a Korean-named folder (지도). Ruby's `unicode_normalize` (used internally by CocoaPods for path handling) can't handle non-ASCII path components reliably, and a downstream `Pod::Executable.execute_command` subprocess call hit the same issue one level deeper (hermes-engine podspec). **Fix: keep the project path ASCII-only.** (This is why the project now lives at `MAP/map-project`, not the original `지도/map-project`.)

2. **Missing native MapLibre SDK — `'MapLibre/MapLibre.h' file not found`**: `@maplibre/maplibre-react-native` v11.x does **not** pull in the native MapLibre iOS SDK via CocoaPods — it injects it as a **Swift Package Manager** dependency from a `post_install` hook (`$MLRN.post_install(installer)`) that the library expects you to add to your own Podfile manually. It's not autolinked and isn't mentioned in the package's own README (only in the external docs site). **Fix**: added the following to `ios/Podfile`'s `post_install` block:
   ```ruby
   $MLRN.post_install(installer)
   ```

3. **Codesign failure — `resource fork, Finder information, or similar detritus not allowed`**: a currently-active, ecosystem-wide bug (affects Flutter too — see `flutter/flutter#180351`, `#181103`, `#189734`) where recent macOS versions tag files from "untrusted" sources (Homebrew, CocoaPods downloads, and apparently anything created by processes in this dev environment's lineage) with a kernel-enforced `com.apple.provenance` extended attribute that **cannot be stripped** by `xattr -d`/`-c` (it silently "succeeds" without actually removing it), and newer Xcode's codesign rejects bundles containing it. **Fix**: disable code signing for simulator builds — it isn't needed there anyway: `CODE_SIGNING_ALLOWED=NO CODE_SIGNING_REQUIRED=NO CODE_SIGN_IDENTITY=""`.

4. **Watchman hangs**: `watchman watch-project` hung indefinitely (0% CPU, not actually crawling) on this project, which made Metro appear stuck at "Waiting for Watchman". **Fix**: stopped and disabled the Watchman LaunchAgent (`launchctl unload -w ~/Library/LaunchAgents/com.github.facebook.watchman.plist`) — Metro falls back to Node's own file watcher without it, and the "Waiting for Watchman" log line turned out to be a harmless periodic retry message, not a hard blocker, once Watchman was out of the picture entirely.

5. **Camera not moving to the initial position — tiles requested at `0/0/0`**: `<Camera centerCoordinate={...} zoomLevel={...} />` silently did nothing (map sat at zoom 0 / world view). The library renamed these props: the current API is `<Camera initialViewState={{ center: [lng, lat], zoom }} />` (`center`/`zoom`, not `centerCoordinate`/`zoomLevel`). Since Metro doesn't type-check, the stale prop names were just silently dropped rather than raising a build error. Confirmed via `xcrun simctl spawn <udid> log show` showing tile requests for `.../planet_osm_line/0/0/0` instead of the expected zoom-13 tiles — that log-based check is the fastest way to diagnose "map renders but shows nothing/wrong area" in the simulator.

6. **Search results dropdown not receiving taps**: `src/search/SearchBox.tsx`'s results list, rendered as a plain absolutely-positioned `View` sibling after `</Map>` (the standard, documented pattern for overlaying UI on a map), never received touches — taps landed but `onPress` never fired, no matter the exact coordinates. This matches a known, unresolved React Native issue (`facebook/react-native#35612`): an absolutely-positioned RN overlay can have its touches swallowed by a native map view sibling underneath it, and no `pointerEvents` combination reliably fixes it. **Fix**: the results dropdown now renders inside a `<Modal transparent animationType="none">` — a genuinely separate native presentation layer, not just a z-index trick — which sidesteps the bug entirely. The search bar itself stays a plain overlay (unaffected by this issue); only the results list is wrapped in the Modal, and only while there's something to show, so the map stays fully interactive the rest of the time.

   **Confirmed working by hand.** Automated tap/text-injection through Claude Code's embedded simulator *panel* was unreliable enough (roughly 1-in-5 success, occasional spurious element-inspector triggers) that it couldn't be trusted as a test signal — turned out that panel is a lightweight preview, not a real interactive input surface (see issue 7 below). Opening the actual **Simulator.app** (`open -a Simulator`) and testing by hand confirmed the full flow works correctly: search → tap a result → camera flies to it → pin drops.

7. **Claude Code's embedded simulator panel is a preview, not a full input surface**: taps/typing sent through it (by both the automation tool *and* the user clicking the panel directly) were unreliable — inconsistent focus, dropped keystrokes, occasional accidental triggering of React Native's dev-mode element inspector. The `iosSimulator` capability was also seen flagged `"unsupported...disabled by its rollout flag"` in the desktop app's own feature-flag list, consistent with this being an early/rollout-gated integration rather than a full remote-control surface. **For any interaction-heavy testing, prefer the real Simulator.app** (`open -a Simulator`, or run from Xcode) over the embedded panel — its clicks/keystrokes go directly to the simulator with no intermediate layer, and behave like a real device.

8. **This dev machine is memory-constrained (8GB total) for this stack**: Xcode + iOS Simulator + Docker (Postgres/Nominatim/Typesense/Martin) + Metro + Claude Code running together can push free RAM to near zero and force active swapping (confirmed via `vm_stat`/`sysctl vm.swapusage` — as low as ~60MB free, 2.4GB in swap, mid-session). This shows up as sluggishness, dropped input, and occasional Simulator crash/reboot — not application bugs. If things feel unresponsive, check `memory_pressure` and close other apps (a browser, Spotify, editors) before assuming something's broken. Colima's Docker VM was tuned down from 4GB (needed transiently for the Nominatim import) to 3GB for ongoing use — see [geocoding/README.md](../geocoding/README.md).
