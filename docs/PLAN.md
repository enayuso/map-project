# Build Plan: Belize Map App ("지도")

*Grounded in [RESEARCH-SUMMARY.md](RESEARCH-SUMMARY.md) and the detailed findings in [research/](research/). This is a living document — update it as decisions get made and phases complete.*

**Status:** 🟢 Scope locked (2026-09-09) — see "Locked decisions" below. Phase 0 is next.

## Guiding principle

Build **one layer at a time, bottom-up**, exactly as the stack is layered in reality: you cannot render a map without tiles, you cannot search without a geocoder, you cannot route without a graph. Each phase should produce something *runnable and visible* before moving to the next — not a paper design.

## Phase 1 — Base Map (Data → Tiles → Render)

2. [x] ~~Generate vector tiles: PostGIS → GeoJSON/flatgeobuf → Tippecanoe → MBTiles~~ **Deviated from plan, deliberately**: Martin serves vector tiles **live, directly from PostGIS** (no Tippecanoe/MBTiles bake step). ## Phase 2 — Search & Geocoding

**Goal:** type an address or place name, get a pin.

1. [x] Stand up **Nominatim** — **done**, chose Nominatim over Pelias (much faster to a working demo, Pelias's multi-service Elasticsearch-backed architecture is overkill at Belize's scale). Full import runs in under 2 minutes. Verified with real queries against both pilot areas (forward search, disambiguation, reverse geocoding with nearest-fallback) — see [geocoding/README.md](../geocoding/README.md) and `scripts/test_geocoding.sh`. Hit and fixed a real bug: Colima's default VM (2GB RAM) couldn't fit Postgres's shared-memory request; resized to 4GB/4CPU.
2. [ ] **Deferred**: from-scratch admin-hierarchy gazetteer. Nominatim's own OSM-derived hierarchy (district → town/village → quarter → road) is already covering this reasonably well in testing — revisit only if real gaps show up, rather than building preemptively.
3. [ ] **Deferred**: libpostal free-text normalization. Nominatim's built-in parsing handled every test query correctly without it. Revisit if messier real-world input (typos, abbreviations, mixed English/Spanish) proves insufficient.
4. [x] Reverse geocoding — **done**, comes free with Nominatim (`/reverse` endpoint). Confirmed the nearest-feature-fallback behavior predicted in [research/03-geocoding-search.md](../docs/research/03-geocoding-search.md) actually happens in practice (an Ambergris Caye test point resolved via a nearby pier, not a road, but still returned a sensible address breakdown).
5. [x] Stand up **Typesense** as the POI/place search index — **done**, chosen over Meilisearch/Elasticsearch per the plan's own reasoning (see [research/03-geocoding-search.md](../docs/research/03-geocoding-search.md)). 3,363 named POIs indexed whole-country from OSM. Verified real typo tolerance (`Sinata` → "Sinatra Restaurant", not just prefix matching) and geo-radius search (489 results within 3km of Belize City) — zero special config needed, this is Typesense's default behavior. See [search/README.md](../search/README.md) and `scripts/reindex_pois.sh`.
   - **Update (2026-09-10)**: supplemented with Overture Maps' Places theme (`scripts/merge_overture_places.py`, optional, run after `reindex_pois.sh`) — adds ~5,850 genuinely new, deduped POIs on top of the OSM base (verified: the same 3km Belize City radius query now returns 1,604 results, up from 489). Each document now carries a `source` field (`osm`/`overture`) for traceability. See [search/README.md](../search/README.md)'s new section for the license reasoning ([research/08-comparative-data-sourcing-landscape.md](research/08-comparative-data-sourcing-landscape.md)) and the dedup mechanics.
6. [x] Define a small, fixed **category taxonomy** — **done**, 18 categories (matches Kakao's model size), mapped from OSM tags in `scripts/build_poi_index.py`. Every document keeps its source OSM tag for traceability; unmapped-but-tagged POIs fall into `other` rather than vanishing. Real breakdown confirms this is genuine Belize data — a small `dive_watersports` category exists specifically because of Ambergris Caye's dive economy.

**Output:** Phase 2's goal — type an address or place name, get a pin — is now backed end-to-end: Nominatim handles addresses/places, Typesense handles POI search-as-you-type, both tested against live Belize data. The gazetteer and libpostal items were tried-and-found-unnecessary rather than skipped, which is worth trusting until real usage says otherwise.

**Client-side wiring — done and confirmed working by hand**: built into the mobile app — a search box ([mobile/src/search/](../mobile/src/search/)) that debounces input, queries both services in parallel, and on selection flies the camera to the result and drops a pin. Along the way, hit and fixed a known React Native bug (`facebook/react-native#35612`) where a native MapView sibling can swallow touches meant for an absolutely-positioned overlay — fixed by rendering the results dropdown in a `Modal` instead. Automated simulator testing in this session was too unreliable to trust as a signal (it turned out Claude Code's embedded simulator *panel* is a lightweight preview, not a full input surface — see [mobile/README.md](../mobile/README.md) issues 6-7); switching to the real **Simulator.app** for manual testing confirmed the full flow works: search → tap a result → camera flies to it → pin drops. **Phase 2 is fully closed.**

Also surfaced a real dev-environment constraint worth carrying forward: this machine's 8GB RAM gets pushed to near-zero free / active swapping when Xcode + Simulator + Docker + Metro + Claude Code all run together, which shows up as sluggish/unresponsive UI — not an app bug. Worth keeping an eye on `memory_pressure`/`vm.swapusage` in later phases rather than assuming a freeze means broken code.

## Phase 3 — POI / Business Data Platform

**Goal:** move from "static OSM snapshot" to a living, maintainable place database. Scoped 2026-09-09 after discussing what a Belize-specific data advantage would actually require — see [research/07-naver-kakao-proprietary-gis.md](research/07-naver-kakao-proprietary-gis.md) for why Naver/Kakao's own MMS-fleet route isn't the relevant comparison here (that tier is for autonomous-driving-grade HD maps; this project needs POI/road accuracy, a much lower and cheaper bar). Two complementary tracks, since they solve different problems:

**Update (2026-09-10)**: [research/08-comparative-data-sourcing-landscape.md](research/08-comparative-data-sourcing-landscape.md) confirms none of Google/Apple/HERE/TomTom/Waze have meaningful first-party Belize coverage either — all lean on OSM/crowdsourcing/licensed imagery, same as this project. Two concrete, low-effort items surfaced worth folding into Track A's thinking without changing the phase's actual scope: (a) the Humanitarian OpenStreetMap Team ran a real, dated building-mapping activation across Cayo/Toledo in mid-2024 (`#belizefires24`, three completed Tasking Manager projects) — **confirmed empirically** (see [06-pilot-region-data-audit.md](research/06-pilot-region-data-audit.md)'s follow-up section): 29% of buildings in the exact target villages were edited in 2024, 99.9% of those inside HOT's documented June–August 2024 window, so this data is genuinely already in our OSM extract, not just claimed; (b) Overture Maps' Places/Addresses theme (CDLA-Permissive-2.0, more permissive than OSM's ODbL) has confirmed, current Belize POI/address data including Meta-sourced businesses with postcodes — a plausible supplementary enrichment source for Phase 2's Typesense index, independent of whether Track B is ever revisited. **(b) is now done** — see Phase 2 item 5's update above; building-data quality in Cayo/Toledo (a) is confirmed adequate as-is, no further action needed there right now.

### Track A — direct OSM contribution (zero build, start immediately)

Fixing genuinely objective map errors — a road with no name, a business that's moved or closed, a missing building — belongs *upstream in OSM itself*, not just in our own database: it benefits the whole OSM commons, and since our entire pipeline (`scripts/fetch_and_clip_osm.sh` → `osm2pgsql` → `scripts/build_poi_index.py`) re-imports from OSM, those fixes flow back into our own map/search/routing data for free on the next re-import — no new code needed to benefit from this.

Two free, iOS-native OSM editor apps make this practical to do in the field, on a phone, without any custom tooling:
- **[Every Door](https://apps.apple.com/us/app/every-door/id1621945342)** — purpose-built for exactly this: quickly add/edit shops, restaurants, and other POIs (name, category, hours, phone), mark places closed. The closest iOS equivalent to Android's well-known StreetComplete (confirmed StreetComplete itself has no iOS release yet, despite active porting work).
- **[Go Map!!](https://github.com/bryceco/GoMap)** — the most-used general-purpose iOS OSM editor; better suited to road-level edits (naming the unnamed roads flagged in [research/06-pilot-region-data-audit.md](research/06-pilot-region-data-audit.md) — only 17% road-name completeness on Ambergris Caye — fixing this directly in OSM is probably the single highest-value use of field time).

Both edit the real, public OpenStreetMap database directly (an OSM account is needed, free to create) — this is the same database every other OSM-based tool in the world reads from, this project included.

### Track B — our own `places` platform (deprioritized 2026-09-09, see below)

**Status: built once, then reverted the same day.** A first version (canonical `places` table, a PostgREST write API, and a "＋ Add/Edit Place" flow in the mobile app itself) was implemented and verified working, then explicitly reverted at your direction: on reflection, an in-app place-adding UI — even one framed as "just for field collection" — has no auth wall distinguishing the operator from any other person who opens the app, and neither Naver nor Kakao actually let ordinary users add places directly. The decision instead: wait for BNSDI's official data to come back (see [research/05-belize-official-data-verification.md](research/05-belize-official-data-verification.md) — an email inquiry is pending as of this date) rather than build our own crowdsourced/self-service data layer right now. The revert (`git revert 53aebee`) removed the table, the API, and the UI, and restored `scripts/reindex_pois.sh`/`build_poi_index.py` to reading straight from `planet_osm_point` again, same as before this track existed.

The scoping below is kept for reference (it's real engineering thinking that may become relevant again — e.g. if BNSDI stays down long-term and the calculus changes) but **is not the current plan**. Track A above is unaffected by this — those are third-party apps editing the public OSM database directly, not a data-entry surface inside our own app, which is a different thing than what item 4 below is.

OSM's data model deliberately doesn't hold things specific to *our* product: verification/freshness status, "claim your business" ownership, click-to-call-formatted contact info, review/rating layers, or anything else that isn't a neutral fact about the physical world. That needs a database we control. Also: any hand-edit made directly against Typesense today gets **silently wiped** on the next `scripts/reindex_pois.sh` run, since that script currently rebuilds straight from a fresh `planet_osm_point` export — there is no durable layer for edits to survive in yet. That's the gap this would close, if/when it's revisited.

1. **New canonical `places` table in PostGIS** — the single source of truth going forward, seeded once from the current OSM-derived POI set (same categorization logic `scripts/build_poi_index.py` already has, pointed at a new destination table instead of straight into Typesense). Schema: `id`, `name`, `category` (reuse the existing 18-category taxonomy), `lat`/`lon`, structured address fields + a free-text informal-description field (landmark-based addressing, per [research/01-data-collection.md](research/01-data-collection.md)), `phone`, `hours`, `website`, `verification_status` (`osm_import` | `field_verified` | `self_registered` | `crowd_suggested`), `source`, `created_at`/`updated_at`/`updated_by`.
2. **A minimal write API** — recommend **PostgREST** (self-hosted, MIT-licensed, auto-generates a full REST CRUD API directly from the `places` table's schema with essentially zero custom backend code) over hand-writing a service, consistent with this project's established pattern of reaching for a proven self-hosted OSS tool before custom-building one. Add hand-written validation/business-rule logic later only where PostgREST's row-level access genuinely isn't enough (e.g. dedup-checking before insert — see item 4).
3. **Typesense becomes a rebuildable cache of `places`, not of raw OSM** — `scripts/reindex_pois.sh` gets re-pointed to export from `places` instead of `planet_osm_point`, so edits/additions persist through reindexes instead of being silently overwritten. Raw OSM re-imports still feed `places` too, just as one more update source, not the only one.
4. **A field-collection "＋ Add/Edit Place" flow in the mobile app itself** — tap the map or use current GPS location, a quick form (name + category required, everything else optional), save → hits the new PostgREST API. This is the first, personal-use version of what later becomes public self-registration/crowdsourcing — same underlying write path, just ungated for now since it's just us. Photo upload and offline queueing (useful given patchy rural connectivity, and `@react-native-async-storage/async-storage` is already integrated from the favorites feature — a local outbox is a natural fit) are real but deferred refinements, not required for a first version.
5. **Public self-registration flow** for business owners — phone OTP + storefront photo, deliberately *not* gated behind a business-registration certificate (Korea's model excludes too much of Belize's informal economy) — once there's an actual user base to draw from.
6. **Crowdsourced "suggest an edit / report an error" flow** with a small human moderation queue — tiered verification (photo required for destructive edits like "mark closed"; lighter touch for additive edits) — same reasoning, needs real traffic first.
7. **Dedup/entity-resolution pass**: `pg_trgm` name-similarity + tight geo-distance threshold to flag likely duplicates, resolved via manual review (not full automation — volume doesn't justify it yet).
8. Consider a modest non-cash incentive for contributions (badges/leaderboard) rather than Naver's cash-equivalent points model, once volume justifies it.

**Recommended build order, if revisited**: items 1-4 first (the durable database + write path), same reasoning as before — no dependency on real users yet. Items 5-8 would still wait for real usage. None of this is scheduled right now; see the status note above.

**Output, if built:** places persist and survive reindexes; owners and users can eventually add/correct places; a moderator can clear a review queue; the POI index from Phase 2 stays fresh from a source we control, not just a frozen OSM snapshot. **Current actual state: none of this exists — Phase 2's original OSM-direct pipeline is what's running.**

## Phase 4 — Routing & Navigation

**Goal:** turn-by-turn directions between two points.

1. [x] Stand up **Valhalla** — **done**, chosen over GraphHopper/OSRM (multiple profiles on one shared graph, no per-profile rebuild, plus built-in map matching). Full-country build took **under a minute** (67 tiles) — dramatically faster than Nominatim's import. See [routing/README.md](../routing/README.md) and `scripts/test_routing.sh`.
2. [x] Configure car/walk/bike routing profiles — **done and verified** with real turn-by-turn output (actual street names: Lakeview Street, Ebony Street, Queen Street Roundabout) for all three profiles, plus a correct 111km cross-country route Belize City → San Ignacio via the real George Price Highway/AR1.
3. [~] Validate turn restrictions/one-way tagging — 36 turn restrictions loaded successfully from the OSM relations (matches the count from [research/06-pilot-region-data-audit.md](../docs/research/06-pilot-region-data-audit.md)'s audit), but **not field-verified against real-world signage** — that needs local ground-truth, not something checkable remotely. Flagged as a known gap, not blocking.
4. [x] Map matching — **done**, confirmed via `/trace_route`: a synthetic 3-point GPS trace correctly snapped to "Queen Street" with a coherent instruction. Zero custom development needed, exactly as [research/04-routing-traffic.md](../docs/research/04-routing-traffic.md) predicted.
5. [x] Static, free-flow-speed ETAs — this is Valhalla's default behavior (no traffic data plugged in), and it's usefully accurate here specifically because `use_default_speeds_config` pulls per-surface-type speeds — which matters given most Belize roads are unpaved per the Phase 0 audit.

**Bonus finding**: routing between the two pilot regions (Belize City ↔ Ambergris Caye/San Pedro, separated by open water) **works** — Valhalla found a real OSM-mapped ferry connection (`has_ferry: true`) rather than failing, confirming the actual water-taxi service tourists use is present in the graph. The route came back long/indirect (253km, ~6.6hrs) though, which suggests the ferry-route OSM data or its road-network connections could use cleanup — worth a closer look before this ships, but the core capability (ferry-aware routing) is real and didn't need special handling.

**Output:** tap two points on the map, get a route + turn-by-turn instructions + a (static) ETA — done both on the backend and in the app. **Client-side wiring**: a "🧭 Directions" button in [mobile/App.tsx](../mobile/App.tsx) lets the user set origin/destination via map taps or search selection, drawing the route line and a bottom-sheet instruction panel (with a 🚗/🚶/🚲 costing switcher) — see [mobile/src/routing/](../mobile/src/routing/). The polyline-decoding/response-parsing logic was independently verified correct against a live Valhalla response (decoded points matched the query's origin/destination exactly, all within Belize's bounding box); the on-device tap interaction still wants the same manual real-Simulator.app spot-check Phase 2's search box needed, for the same reason (see [mobile/README.md](../mobile/README.md) issues 6-8).

**Update (2026-09-10)**: replaced the implicit "first search picks origin, second picks destination" flow with an explicit Naver/Kakao-style two-field route card (`src/routing/DirectionsSearchPanel.tsx`) — independently searchable/tappable origin and destination fields, a "use current location" shortcut, and a swap button, so either endpoint can be set in any order with visible feedback about what's already picked, rather than a hint text and a silent pin. Also added a third way to set either field — "🗺️ Select on map" (`src/routing/MapPointPicker.tsx`), Naver/Kakao's own 지도에서 선택: a pin fixed at screen center while the map pans underneath it, reverse-geocoding (new Nominatim-backed `reverseGeocode()`) whatever ends up under the pin. See [mobile/README.md](../mobile/README.md)'s Directions section for the full writeup.

## Phase 4.5 — UX Polish Toward Kakao/Naver Parity

Not one of the original five phases — this is the first round of "make it behave like Kakao/Naver Map" polish, requested directly once Phases 1/2/4 were working end-to-end. Expect more items to land here over time.

1. [x] **Whole-country coverage** — turned out to already be done: all four backend services (Martin tiles, Nominatim, Typesense, Valhalla) were built from the *full* Belize OSM extract back in Phases 1/2/4, not just the two pilot bboxes used for testing focus. Confirmed with real queries against towns neither pilot area covers — Belmopan (the capital) geocodes correctly, Punta Gorda (south) and Corozal (north) both geocode correctly, a Belize City → Corozal route computes correctly (138km), and tiles render correctly near Belmopan. The "pilot region" framing in this doc was always a *testing* scope, never an actual data restriction — updated `mobile/App.tsx`'s comments to reflect that the whole country is live today.
2. [x] **Current-location detection** — added via MapLibre Native's built-in `useCurrentPosition` hook + `<NativeUserLocation mode="heading">` (no extra geolocation package needed). Deferred starting location tracking until the user taps the new 📍 button (bottom-right), so the OS permission prompt doesn't fire before it's actually needed. Filled in the previously-empty `NSLocationWhenInUseUsageDescription` in `Info.plist` (required a rebuild, not just a Metro refresh, since Info.plist is baked in at build time).
3. [x] **Compass / reset-bearing control** — turned out to be a **built-in native ornament**, not custom work: `<Map compass compassHiddenFacingNorth compassPosition={{top: 60, right: 12}}>`. Appears only when the map is rotated away from north, hides itself when facing north (confirmed working — no compass visible at the default north-up view), and tapping it resets bearing to north natively. Being a native map ornament rather than an RN sibling view, it's also immune to the touch-passthrough bug documented in `mobile/README.md` issue 6.
4. [x] **Place detail card + tap-to-query POIs** — the core Kakao/Naver interaction: tap a place (search result *or* a POI rendered directly on the map) and get a bottom-sheet card with name/category, an inline travel-time preview from the user's current location, and Directions/Close actions. Two parts:
   - Added `poi-circles`/`poi-labels` layers to [styles/basic.json](../styles/basic.json) (synced to `mobile/src/styles/basic.json`) — previously the style only rendered `place-labels` (settlements/neighborhoods), no individual businesses/amenities, so there was nothing on the map itself to tap. Now any point tagged `amenity`/`shop`/`tourism` (with a name) shows as a small dot from zoom 15, labeled from zoom 16.
   - New [mobile/src/places/PlaceCard.tsx](../mobile/src/places/PlaceCard.tsx) component, wired into `mobile/App.tsx`: map taps now call `mapRef.current.queryRenderedFeatures(point, {layers: ['poi-circles']})` (MapLibre Native's built-in hit-testing) when not in routing mode, converting any hit into the same `SearchResult` shape a search selection produces — so search results and map-tapped POIs flow through one card component. The travel-time preview reuses `fetchRoute` (Valhalla, `auto` costing) from the user's live position, refetching whenever the selected place or position changes; it degrades to a "tap 📍 to enable" hint if location hasn't been turned on yet. "Directions" from the card feeds straight into the existing routing flow (sets it as the destination, opens the directions panel).
   - Follows the same `<Modal>` pattern established for `SearchBox`'s dropdown and `RoutePanel`, for the same reason (native `MapView` sibling touch-swallowing, `facebook/react-native#35612` — see `mobile/README.md` issue 6).
   - **Verified**: TypeScript compiles clean against the actual installed `@maplibre/maplibre-react-native` types (`MapRef.queryRenderedFeatures`, `PressEvent.point`) — confirmed by reading the library's own `.d.ts` rather than assuming the API shape. App relaunches and renders without crashing after the change (pure JS + style-JSON, no rebuild needed). The interactive tap-through (search → card → directions, and map-POI tap → card) still needs the same manual real-Simulator.app spot-check as every prior UI feature — see `mobile/README.md` issues 6-8; this session's automated tap injection reproduced issue 7 again (spurious React Native dev menu) while attempting it.
5. ## Phase 5 — Deferred / Future Layers

These require data that doesn't exist yet and shouldn't block earlier phases:

- **Real-time traffic**: only viable once the app has enough active users to serve as its own crowdsourced probe-data source (a multi-year horizon). Historical speed-profile-based ETA blending is a prerequisite step before any live layer.
- **Public transit directions**: no GTFS feed exists for Belize anywhere — there's no metro/train at all, only bus, and even bus schedule data would need to be hand-authored (digitizing third-party sites like belizebusschedules.com) before OpenTripPlanner/RAPTOR-style routing is possible. Confirmed with you (2026-09-09) to leave this deferred rather than tackle it now — the data-authoring cost is real and separate from anything else in this app.
- **Street-level imagery ("Belize Street View")**: a lean single-vehicle 360°-camera + GPS rig covering main highways/town centers — Kakao's 2008-era approach, not Naver's current LiDAR-heavy fleet — is the realistic model, and still a meaningful post-launch investment, not a v1 item.
- **Offline maps**: bundle a pre-baked national MBTiles/PMTiles file with the mobile app, refreshed from the same Tippecanoe pipeline — cheap to add once Phase 1's tile pipeline exists, worth doing given Belize's low-connectivity rural/dive-site areas.

## Locked decisions (2026-09-09)

1. **Geographic scope for v1: pilot region for testing focus, whole country for actual data.** Working definition was **Belize City + a tourist corridor (Ambergris Caye/San Pedro)** — but every backend service was built from the full-country OSM extract from the start, and Phase 4.5 confirmed the whole country already works end-to-end (Belmopan, Corozal, Punta Gorda all resolve correctly). The pilot bboxes were always a *QA/testing* scope, not a data limitation.
2. **Platform priority: mobile first (iOS + Android).** This changes Phase 1's client target from "MapLibre GL JS in a browser" to **MapLibre Native**. For a solo/small-team build targeting both platforms from one codebase, we went with **React Native** + `@maplibre/maplibre-react-native` — **now locked, not just a recommendation**: it's built and running (see Phase 1 below, [mobile/](../mobile/)).
3. **Budget: hobby/self-funded now, may scale up if the pilot succeeds.** This means every Phase 0–4 choice should default to **free-tier and self-hosted options that remain valid if the project later needs to scale commercially** — i.e., avoid anything free-for-non-commercial-use-only that would need ripping out later. Concretely: **Sentinel-2/Copernicus imagery** (free, ~10m resolution, license explicitly permits commercial use) instead of a commercial provider for the pilot's satellite layer, self-hosted OSS (PostGIS, Martin, Nominatim/Pelias, Typesense/Meilisearch, Valhalla/GraphHopper) on modest/free-tier cloud infra rather than paid SaaS equivalents. Revisit Maxar/Airbus/Planet imagery licensing only once the pilot has traction and a real budget.
4. **Project nature: commercial venture.** This has two direct licensing consequences to respect from day one: (a) **OpenStreetMap's ODbL license permits commercial use** but requires attribution and share-alike *of the database itself* if it's redistributed/published — fine for "using OSM data to power an app," just needs a visible attribution in the app; (b) every tool in the recommended stack (MapLibre, Valhalla/GraphHopper, Typesense/Meilisearch, libpostal, Pelias) is chosen specifically because its license (BSD/MIT/Apache-2.0) permits commercial use with no fee — this was already true of the Phase-0-recommended stack, and is now a hard constraint rather than just a preference, since we're no longer picking tools "for a hobby project."
5. **Team**: solo build with Claude as engineering partner, proceeding phase by phase.
