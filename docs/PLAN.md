# Build Plan: Belize Map App ("지도")

*Grounded in [RESEARCH-SUMMARY.md](RESEARCH-SUMMARY.md) and the detailed findings in [research/](research/). This is a living document — update it as decisions get made and phases complete.*

**Status:** 🟢 Scope locked (2026-09-09) — see "Locked decisions" below. Phase 0 is next.

## Guiding principle

Build **one layer at a time, bottom-up**, exactly as the stack is layered in reality: you cannot render a map without tiles, you cannot search without a geocoder, you cannot route without a graph. Each phase should produce something *runnable and visible* before moving to the next — not a paper design.

## Phase 1 — Base Map (Data → Tiles → Render)

**Goal:** a pannable, zoomable map of the pilot region in a mobile app (iOS + Android), styled, with no search or routing yet.

1. [x] Import the OSM extract via `osm2pgsql` into PostGIS. **Done** — full-country extract loaded (not just the pilot bboxes: only 18MB, no reason not to have the whole country in the canonical store; tile queries are still scoped to the pilot region at render time). See [backend/](../backend/).
2. [x] ~~Generate vector tiles: PostGIS → GeoJSON/flatgeobuf → Tippecanoe → MBTiles~~ **Deviated from plan, deliberately**: Martin serves vector tiles **live, directly from PostGIS** (no Tippecanoe/MBTiles bake step). At this data size that's simpler to iterate on (data changes are visible immediately, no rebake) — the static-bake pipeline is deferred to Phase 5 (offline maps), where it belongs anyway. See [backend/README.md](../backend/README.md), including a **known Colima-networking gotcha** (direct Postgres connections from the host fail; HTTP to Martin works fine) and its workaround (`scripts/db_exec.sh`).
3. [x] Serve tiles via **Martin** — done, configured via [`backend/martin-config.yaml`](../backend/martin-config.yaml) to publish only our tables. CDN fronting deferred until there's a real deployment target.
4. [x] Scaffold a **React Native** app with `@maplibre/maplibre-react-native` — **done and running**. Xcode installed (26.6) and set up by you; the app ([mobile/](../mobile/)) builds and runs in the iOS Simulator, rendering the real Belize City map (roads, buildings, water, neighborhood labels) from our own PostGIS+Martin backend, confirmed interactive (pinch-zoom tested live in-simulator). Getting here hit five real, non-obvious environment bugs (non-ASCII project path breaking CocoaPods/Ruby, a missing manual Podfile hook for MapLibre's native SDK, a currently-active macOS/Xcode codesign bug, a Watchman hang, and a silently-wrong Camera prop name) — all documented with fixes in [mobile/README.md](../mobile/README.md) so they aren't re-debugged from scratch next time (e.g. adding Android).
5. [ ] Add a **Sentinel-2** satellite-imagery raster layer as a togglable base-map option (free, commercial-use-permitted — see "Locked decisions"). Not started.
6. [ ] Stretch: a day/night or "tourist" alternate style. Not started.
7. [ ] Android build — not attempted yet (this phase focused on getting iOS working first, per your call). `mobile/android/` exists from the RN scaffold but is unbuilt/unverified.

**Output so far:** Phase 1's actual goal is met — **a pannable, zoomable, styled map of Belize City running natively in the iOS Simulator**, backed by our own data pipeline end to end (OSM → PostGIS → Martin → MapLibre Native). The web preview ([web-preview/](../web-preview/)) remains as a lighter-weight way to sanity-check style/tile changes without a full native rebuild. Satellite toggle and Android are the remaining open items before Phase 1 is fully closed out.

## Phase 2 — Search & Geocoding

**Goal:** type an address or place name, get a pin.

1. [x] Stand up **Nominatim** — **done**, chose Nominatim over Pelias (much faster to a working demo, Pelias's multi-service Elasticsearch-backed architecture is overkill at Belize's scale). Full import runs in under 2 minutes. Verified with real queries against both pilot areas (forward search, disambiguation, reverse geocoding with nearest-fallback) — see [geocoding/README.md](../geocoding/README.md) and `scripts/test_geocoding.sh`. Hit and fixed a real bug: Colima's default VM (2GB RAM) couldn't fit Postgres's shared-memory request; resized to 4GB/4CPU.
2. [ ] **Deferred**: from-scratch admin-hierarchy gazetteer. Nominatim's own OSM-derived hierarchy (district → town/village → quarter → road) is already covering this reasonably well in testing — revisit only if real gaps show up, rather than building preemptively.
3. [ ] **Deferred**: libpostal free-text normalization. Nominatim's built-in parsing handled every test query correctly without it. Revisit if messier real-world input (typos, abbreviations, mixed English/Spanish) proves insufficient.
4. [x] Reverse geocoding — **done**, comes free with Nominatim (`/reverse` endpoint). Confirmed the nearest-feature-fallback behavior predicted in [research/03-geocoding-search.md](../docs/research/03-geocoding-search.md) actually happens in practice (an Ambergris Caye test point resolved via a nearby pier, not a road, but still returned a sensible address breakdown).
5. [x] Stand up **Typesense** as the POI/place search index — **done**, chosen over Meilisearch/Elasticsearch per the plan's own reasoning (see [research/03-geocoding-search.md](../docs/research/03-geocoding-search.md)). 3,363 named POIs indexed whole-country. Verified real typo tolerance (`Sinata` → "Sinatra Restaurant", not just prefix matching) and geo-radius search (489 results within 3km of Belize City) — zero special config needed, this is Typesense's default behavior. See [search/README.md](../search/README.md) and `scripts/reindex_pois.sh`.
6. [x] Define a small, fixed **category taxonomy** — **done**, 18 categories (matches Kakao's model size), mapped from OSM tags in `scripts/build_poi_index.py`. Every document keeps its source OSM tag for traceability; unmapped-but-tagged POIs fall into `other` rather than vanishing. Real breakdown confirms this is genuine Belize data — a small `dive_watersports` category exists specifically because of Ambergris Caye's dive economy.

**Output:** Phase 2's goal — type an address or place name, get a pin — is now backed end-to-end: Nominatim handles addresses/places, Typesense handles POI search-as-you-type, both tested against live Belize data. The gazetteer and libpostal items were tried-and-found-unnecessary rather than skipped, which is worth trusting until real usage says otherwise.

**Client-side wiring — done and confirmed working by hand**: built into the mobile app — a search box ([mobile/src/search/](../mobile/src/search/)) that debounces input, queries both services in parallel, and on selection flies the camera to the result and drops a pin. Along the way, hit and fixed a known React Native bug (`facebook/react-native#35612`) where a native MapView sibling can swallow touches meant for an absolutely-positioned overlay — fixed by rendering the results dropdown in a `Modal` instead. Automated simulator testing in this session was too unreliable to trust as a signal (it turned out Claude Code's embedded simulator *panel* is a lightweight preview, not a full input surface — see [mobile/README.md](../mobile/README.md) issues 6-7); switching to the real **Simulator.app** for manual testing confirmed the full flow works: search → tap a result → camera flies to it → pin drops. **Phase 2 is fully closed.**

Also surfaced a real dev-environment constraint worth carrying forward: this machine's 8GB RAM gets pushed to near-zero free / active swapping when Xcode + Simulator + Docker + Metro + Claude Code all run together, which shows up as sluggish/unresponsive UI — not an app bug. Worth keeping an eye on `memory_pressure`/`vm.swapusage` in later phases rather than assuming a freeze means broken code.

## Phase 3 — POI / Business Data Platform

**Goal:** move from "static OSM snapshot" to a living, maintainable place database.

1. Design the place schema: name, category, coordinates, address (structured + informal-description field), phone, hours, verification status, source (OSM/self-registered/field-collected).
2. Build a **lightweight self-registration flow** for business owners — phone OTP + storefront photo, deliberately *not* gated behind a business-registration certificate (Korea's model excludes too much of Belize's informal economy).
3. Build a **crowdsourced "suggest an edit / report an error" flow** with a small human moderation queue — tiered verification (photo required for destructive edits like "mark closed"; lighter touch for additive edits).
4. Build a **dedup/entity-resolution pass**: `pg_trgm` name-similarity + tight geo-distance threshold to flag likely duplicates, resolved via manual review (not full automation — volume doesn't justify it yet).
5. Consider a modest non-cash incentive for contributions (badges/leaderboard) rather than Naver's cash-equivalent points model, until volume justifies a paid rewards system.

**Output:** owners and users can add/correct places; a moderator can clear a review queue; the POI index from Phase 2 stays fresh.

## Phase 4 — Routing & Navigation

**Goal:** turn-by-turn directions between two points.

1. [x] Stand up **Valhalla** — **done**, chosen over GraphHopper/OSRM (multiple profiles on one shared graph, no per-profile rebuild, plus built-in map matching). Full-country build took **under a minute** (67 tiles) — dramatically faster than Nominatim's import. See [routing/README.md](../routing/README.md) and `scripts/test_routing.sh`.
2. [x] Configure car/walk/bike routing profiles — **done and verified** with real turn-by-turn output (actual street names: Lakeview Street, Ebony Street, Queen Street Roundabout) for all three profiles, plus a correct 111km cross-country route Belize City → San Ignacio via the real George Price Highway/AR1.
3. [~] Validate turn restrictions/one-way tagging — 36 turn restrictions loaded successfully from the OSM relations (matches the count from [research/06-pilot-region-data-audit.md](../docs/research/06-pilot-region-data-audit.md)'s audit), but **not field-verified against real-world signage** — that needs local ground-truth, not something checkable remotely. Flagged as a known gap, not blocking.
4. [x] Map matching — **done**, confirmed via `/trace_route`: a synthetic 3-point GPS trace correctly snapped to "Queen Street" with a coherent instruction. Zero custom development needed, exactly as [research/04-routing-traffic.md](../docs/research/04-routing-traffic.md) predicted.
5. [x] Static, free-flow-speed ETAs — this is Valhalla's default behavior (no traffic data plugged in), and it's usefully accurate here specifically because `use_default_speeds_config` pulls per-surface-type speeds — which matters given most Belize roads are unpaved per the Phase 0 audit.

**Bonus finding**: routing between the two pilot regions (Belize City ↔ Ambergris Caye/San Pedro, separated by open water) **works** — Valhalla found a real OSM-mapped ferry connection (`has_ferry: true`) rather than failing, confirming the actual water-taxi service tourists use is present in the graph. The route came back long/indirect (253km, ~6.6hrs) though, which suggests the ferry-route OSM data or its road-network connections could use cleanup — worth a closer look before this ships, but the core capability (ferry-aware routing) is real and didn't need special handling.

**Output:** tap two points on the map, get a route + turn-by-turn instructions + a (static) ETA — done both on the backend and in the app. **Client-side wiring**: a "🧭 Directions" button in [mobile/App.tsx](../mobile/App.tsx) lets the user set origin/destination via map taps or search selection, drawing the route line and a bottom-sheet instruction panel (with a 🚗/🚶/🚲 costing switcher) — see [mobile/src/routing/](../mobile/src/routing/). The polyline-decoding/response-parsing logic was independently verified correct against a live Valhalla response (decoded points matched the query's origin/destination exactly, all within Belize's bounding box); the on-device tap interaction still wants the same manual real-Simulator.app spot-check Phase 2's search box needed, for the same reason (see [mobile/README.md](../mobile/README.md) issues 6-8).

Deferred starting location tracking until the user taps the new 📍 button (bottom-right), so the OS permission prompt doesn't fire before it's actually needed. 3. [x] **Compass / reset-bearing control** — turned out to be a **built-in native ornament**, not custom work: `<Map compass compassHiddenFacingNorth compassPosition={{top: 60, right: 12}}>`. 4. [x] **Place detail card + tap-to-query POIs** — the core Kakao/Naver interaction: tap a place (search result *or* a POI rendered directly on the map) and get a bottom-sheet card with name/category, an inline travel-time preview from the user's current location, and Directions/Close actions. Two parts:

Now any point tagged `amenity`/`shop`/`tourism` (with a name) shows as a small dot from zoom 15, labeled from zoom 16.
   - New [mobile/src/places/PlaceCard.tsx](../mobile/src/places/PlaceCard.tsx) component, wired into `mobile/App.tsx`: map taps now call `mapRef.current.queryRenderedFeatures(point, {layers: ['poi-circles']})` (MapLibre Native's built-in hit-testing) when not in routing mode, converting any hit into the same `SearchResult` shape a search selection produces — so search results and map-tapped POIs flow through one card component. The travel-time preview reuses `fetchRoute` (Valhalla, `auto` costing) from the user's live position, refetching whenever the selected place or position changes; it degrades to a "tap 📍 to enable" hint if location hasn't been turned on yet. "Directions" from the card feeds straight into the existing routing flow (sets it as the destination, opens the directions panel).
   - Follows the same `<Modal>` pattern established for `SearchBox`'s dropdown and `RoutePanel`, for the same reason (native `MapView` sibling touch-swallowing, `facebook/react-native#35612` — see `mobile/README.md` issue 6).
   - **Verified**: TypeScript compiles clean against the actual installed `@maplibre/maplibre-react-native` types (`MapRef.queryRenderedFeatures`, `PressEvent.point`) — confirmed by reading the library's own `.d.ts` rather than assuming the API shape. App relaunches and renders without crashing after the change (pure JS + style-JSON, no rebuild needed). The interactive tap-through (search → card → directions, and map-POI tap → card) still needs the same manual real-Simulator.app spot-check as every prior UI feature — see `mobile/README.md` issues 6-8; this session's automated tap injection reproduced issue 7 again (spurious React Native dev menu) while attempting it.
5. [x] **Category quick-filter browsing** — the other everyday Kakao/Naver interaction, arguably used more than typed search: a horizontal chip bar (🍽 Food, ☕ Cafes, 🛒 Grocery, ⛽ Gas, 🏧 Bank/ATM, 💊 Pharmacy, 🏨 Hotels, 🎡 Attractions, 🍺 Bars, 🏥 Health) under the search box. Tapping a pin or list row opens the same `PlaceCard` as search/map-tap selection. No new data or backend work — reuses the 18-category Typesense taxonomy from Phase 2 (`scripts/build_poi_index.py`) and the geo-radius filter syntax already proven in `search/README.md`.

New `searchNearby()` in `mobile/src/search/api.ts`.

The chip-tap → results-sheet interaction itself still needs a manual real-Simulator.app pass — automated tap injection in this session didn't register on the chip at all this time (no request reached Typesense per its own logs), a milder variant of the same issue 7 unreliability, not a code defect.

6. [x] **Zoom control** — a stacked +/− button on the right edge above the 📍 locate button, matching Kakao/Naver's own zoom control placement/shape. Uses `CameraRef.zoomTo(zoom, {duration})` (confirmed real against the library's `.d.ts`, same verification approach as item 4's `queryRenderedFeatures`), with live zoom tracked via `<Map onRegionDidChange>` so the buttons disable themselves at the configured bounds (zoom 9-19, see item 8 for why 9) and stay accurate through pinch-zoom, double-tap-zoom, and every other camera move already in the app. Native pinch/double-tap zoom (MapLibre's defaults) are untouched — this is the explicit-tap alternative both apps offer *alongside* gestures.

Tap-through itself needs the same manual real-Simulator.app check as everything else here — automated tap injection didn't produce a visible zoom change this attempt (issue 7-style unreliability, not a defect in the zoomTo/onRegionDidChange wiring, which is independently confirmed correct via the library's own types).

**Verification note**: as with Phases 2/4, on-device tap interaction (the 📍 button, map rotation, place cards, category chips, zoom buttons) should get the same manual real-Simulator.app spot-check rather than trusting automated tap injection — see `mobile/README.md` issues 6-8 for why.

7. [x] **Sea/ocean rendering fix** — you noticed the water looked wrong (small blue lagoon spots, but the actual Caribbean Sea rendering as plain beige background) and asked why. Root cause: OSM stores coastline as *lines*, not a ready-made sea polygon, and osm2pgsql's classic import (Phase 1) never assembles those lines into polygons — a deliberate upstream omission, confirmed by checking (2,202 `natural=coastline` ways exist in our raw extract; zero made it into `planet_osm_line` after import). Fixed by loading the community-maintained global water-polygon dataset (ODbL, same license as our other OSM data), clipped to Belize, as a new `water_polygons` table + Martin source + `sea` style layer. See [backend/README.md](../backend/README.md)'s new `water_polygons` section for the full story, including why running `osmcoastline` directly on our own small extract first gave the *wrong* answer (it classified mainland Belize itself as water — a country's coastline only closes into a correct ring using its land-border data with neighboring countries, which isn't in a country-sized extract at all). Verified with point-in-polygon checks against real coordinates (a San Pedro business → correctly land; open Caribbean Sea → correctly water) before wiring it in, then confirmed visually in the simulator: the whole coastline now renders correctly.
   - One-time tooling note: `osmcoastline` (GPL-3.0) was installed and tried during diagnosis, in the same "offline data-processing tool, not shipped with the app" role `osm2pgsql` (also GPL) already plays for the rest of this pipeline — consistent with Locked Decision 4's commercial-license constraint, which has always applied to what's *running as part of the product*, not one-time import tooling. It wasn't needed in the end (the precomputed dataset approach won), so it isn't a dependency of anything in `scripts/`.
8. [x] **Zoomed-out UX cleanup + bold country border** — fixing item 7 surfaced a second, related problem: zooming all the way out looked broken, for two independent reasons, both fixed together:
   - **Label clutter**: `place-labels` had no `minzoom`/significance filtering at all, so every settlement — down to tiny hamlets — rendered its name at every zoom level, creating unreadable clutter zoomed out (this is what actually made the shared screenshot look overwhelming, more than the edge itself). Replaced with four tiered layers in `styles/basic.json` by OSM's own `place` tag hierarchy (checked the real data first: 4 `city`, 16 `town`, 213 `village`, the rest hamlet/locality/suburb/neighbourhood/quarter) — `place-labels-major` (cities, bold, visible from zoom 0), `-town` (zoom 7+), `-village` (zoom 10+), `-minor` (everything else, zoom 13+). This is standard cartographic practice (label prioritization by significance) that Kakao/Naver already do — you never see a random hamlet's name at country-zoom in a real map app.
   - **Hard edge at the sea layer's clip boundary**: the new `sea` layer (item 7) has real data only within roughly Belize's own extent, so zooming out far enough eventually revealed a stark rectangular edge — the visible symptom in the screenshot you shared. Since we don't have neighboring countries' land data, extending the sea polygon further isn't safe (it would render Mexico/Guatemala/Honduras as if they were underwater, wrong in a different, worse way — misrepresenting real geography instead of just having a visible data boundary). Fixed instead the way a limited-coverage map app actually should: capped how far out you can go. `mobile/App.tsx` now sets `<Camera minZoom={9} maxZoom={19} maxBounds={...}>` — `minZoom` applies to pinch/double-tap zoom too, not just the +/- buttons (previously only the buttons were clamped), and is calibrated (not guessed) against the sea layer's real extent and this screen size so the edge stays out of view during ordinary browsing. `maxBounds` matches the sea layer's own extent, stopping the map from panning into the empty void beyond it — deliberately *not* shrunk tighter than that, since real towns we've already tested (Corozal, Punta Gorda) sit near the country's extremes and need to stay reachable; a residual sliver of edge is still possible if you pan all the way to one of those while also fully zoomed out, an accepted trade-off over breaking navigation.
   - **Bold country border**: added, per your request, matching how Kakao/Naver visually ground the map to "this is the country we cover" — a new `country-border` line layer in `styles/basic.json`, filtered to `boundary=administrative`/`admin_level=2` from the existing `planet_osm_line` source (confirmed present: Belize's shared border ways with Mexico and Guatemala, including the border rivers — Río Hondo, Sarstoon River — are already in our OSM extract), styled as a bold dashed maroon line, zoom-scaled width.
   - **Verified**: style JSON is valid and loads without any `mbgl`/style-parse errors in the device log after reload (checked directly, not assumed). TypeScript/ESLint clean. Bold `Belize City` label and the sea/border layers all confirmed rendering correctly via simulator screenshot. The zoom/pan bounds themselves are a native `<Camera>` constraint (not custom touch handling our own code could get wrong), verified by reading `CameraProps`'s real type definitions rather than assumed — but like every interactive behavior this session, the *actual* zoomed-out feel needs your manual confirmation in the real Simulator.app, since this session's automated tap injection couldn't reliably drive repeated zoom-out taps to test it live (see `mobile/README.md` issues 6-8).
9. [x] **Favorites + recent searches** — the "save for later" half of the Kakao/Naver interaction set (search, category browsing, directions, and now bookmarking), local-only, no backend work. A ★ button on `PlaceCard` saves/unsaves the current place; `SearchBox`, when focused with an empty query, now shows "⭐ Saved places" and "🕐 Recent" sections instead of nothing — the same shortcut both apps show before you start typing. Persisted via `@react-native-async-storage/async-storage` (MIT, new native dependency — the first since MapLibre itself, needed a real rebuild not just a Metro reload) in `mobile/src/places/favorites.ts`; `App.tsx` owns the actual `favorites`/`recentSearches` state (loaded once on mount) so `SearchBox` and `PlaceCard` always agree on it rather than each reading storage independently. Any place selection — typed search, category-chip tap, or a direct map-POI tap — records a "recent," matching how Kakao/Naver's own recents track anything you've looked at, not just typed queries.
   - Fixed one existing behavior along the way that would have undercut this feature: `SearchBox` used to fill its own text field with the selected place's name after a selection, meaning the box was rarely actually *empty* again — so the new recents/favorites shortcut would have rarely had a chance to show. Changed it to clear back to empty instead (the place now shows on the map/its card, not duplicated in the search bar), matching how Kakao/Naver's own search boxes behave.
   - **Verified**: TypeScript/ESLint clean. Native module confirmed initializing correctly post-rebuild — its storage directory (`RCTAsyncLocalStorage_V1`) appears in the device log with zero errors, direct evidence it's actually persisting to disk, not just failing to crash. App relaunches and renders correctly after a full native rebuild (`pod install` + `xcodebuild`, required this time since this is a real native dependency). ## Phase 5 — Deferred / Future Layers

These require data that doesn't exist yet and shouldn't block earlier phases:

- **Real-time traffic**: only viable once the app has enough active users to serve as its own crowdsourced probe-data source (a multi-year horizon). Historical speed-profile-based ETA blending is a prerequisite step before any live layer.
- **Public transit directions**: no GTFS feed exists for Belize anywhere — there's no metro/train at all, only bus, and even bus schedule data would need to be hand-authored (digitizing third-party sites like belizebusschedules.com) before OpenTripPlanner/RAPTOR-style routing is possible. Confirmed with you (2026-09-09) to leave this deferred rather than tackle it now — the data-authoring cost is real and separate from anything else in this app.
- **Street-level imagery ("Belize Street View")**: a lean single-vehicle 360°-camera + GPS rig covering main highways/town centers — Kakao's 2008-era approach, not Naver's current LiDAR-heavy fleet — is the realistic model, and still a meaningful post-launch investment, not a v1 item.
- **Offline maps**: bundle a pre-baked national MBTiles/PMTiles file with the mobile app, refreshed from the same Tippecanoe pipeline — cheap to add once Phase 1's tile pipeline exists, worth doing given Belize's low-connectivity rural/dive-site areas.

## Recommended stack (subject to Phase 0 confirmation)

| Layer | Choice | Why |
|---|---|---|
| Geodata store | PostgreSQL + PostGIS | Industry standard, everything else plugs into it |
| Base data | OpenStreetMap extract (Geofabrik/HOT) | Only viable geometry/POI source for Belize |
| Tile generation | Tippecanoe → MBTiles, OpenMapTiles schema | Small country = tiny extract; static pre-bake beats a live dynamic server |
| Tile serving | Martin (or tileserver-gl) + CDN | Fast, low-ops, handles both static MBTiles and PMTiles |
| Client renderer | MapLibre Native, via React Native bindings (mobile-first) | License-clean (BSD), WebGL/OpenGL, same model as Naver/Kakao's modern SDKs; one codebase for iOS+Android |
| Satellite imagery | Sentinel-2/Copernicus (free, commercial-use-permitted) for pilot | Upgrade to Maxar/Airbus/Planet only once budget allows post-pilot |
| Geocoding | **Nominatim** (chosen over Pelias — faster to a working demo, sufficient so far without libpostal) | Mature OSS reference implementation of the exact algorithm shape Kakao/Naver use |
| POI search | **Typesense** (chosen over Meilisearch/Elasticsearch) | Lighter than Elasticsearch at Belize's POI volume, built-in typo tolerance verified working |
| Routing | **Valhalla** (chosen over GraphHopper/OSRM) | Multiple profiles on one shared graph, built-in map matching — both verified working, under a minute to build for all of Belize |
| Dedup | PostgreSQL `pg_trgm` + manual review queue | Volume doesn't justify ML entity resolution yet |

## Locked decisions (2026-09-09)

1. **Geographic scope for v1: pilot region for testing focus, whole country for actual data.** Working definition was **Belize City + a tourist corridor (Ambergris Caye/San Pedro)** — but every backend service was built from the full-country OSM extract from the start, and Phase 4.5 confirmed the whole country already works end-to-end (Belmopan, Corozal, Punta Gorda all resolve correctly). The pilot bboxes were always a *QA/testing* scope, not a data limitation.
2. **Platform priority: mobile first (iOS + Android).** This changes Phase 1's client target from "MapLibre GL JS in a browser" to **MapLibre Native**. For a solo/small-team build targeting both platforms from one codebase, we went with **React Native** + `@maplibre/maplibre-react-native` — **now locked, not just a recommendation**: it's built and running (see Phase 1 below, [mobile/](../mobile/)).
3. **Budget: hobby/self-funded now, may scale up if the pilot succeeds.** This means every Phase 0–4 choice should default to **free-tier and self-hosted options that remain valid if the project later needs to scale commercially** — i.e., avoid anything free-for-non-commercial-use-only that would need ripping out later. Concretely: **Sentinel-2/Copernicus imagery** (free, ~10m resolution, license explicitly permits commercial use) instead of a commercial provider for the pilot's satellite layer, self-hosted OSS (PostGIS, Martin, Nominatim/Pelias, Typesense/Meilisearch, Valhalla/GraphHopper) on modest/free-tier cloud infra rather than paid SaaS equivalents. Revisit Maxar/Airbus/Planet imagery licensing only once the pilot has traction and a real budget.
4. **Project nature: commercial venture.** This has two direct licensing consequences to respect from day one: (a) **OpenStreetMap's ODbL license permits commercial use** but requires attribution and share-alike *of the database itself* if it's redistributed/published — fine for "using OSM data to power an app," just needs a visible attribution in the app; (b) every tool in the recommended stack (MapLibre, Valhalla/GraphHopper, Typesense/Meilisearch, libpostal, Pelias) is chosen specifically because its license (BSD/MIT/Apache-2.0) permits commercial use with no fee — this was already true of the Phase-0-recommended stack, and is now a hard constraint rather than just a preference, since we're no longer picking tools "for a hobby project."
5. **Team**: solo build with Claude as engineering partner, proceeding phase by phase.
