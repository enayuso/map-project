# Location Sharing, Shared Lists, Hazard Reports, POI Corrections & Curated Reference Data (Phase 4.5)

Six things, one small service: live "share my location with someone" (Naver/Kakao both have this — Kakao's own "친구위치" just had its time limit removed entirely, per [docs/research/09-kakao-naver-feature-audit.md](../docs/research/09-kakao-naver-feature-audit.md)), shareable saved-place lists (Naver's own Dec 2022 favorites-folder upgrade), crowdsourced road hazard reports (Waze's core idea, added 2026-09-10 per [docs/research/10-remaining-feature-gaps.md](../docs/research/10-remaining-feature-gaps.md) — a genuinely undocumented-anywhere-digital gap for Belize's flooding/washouts/checkpoints), a crowd-sourced POI correction queue (added 2026-09-10 per [docs/research/11-kakao-naver-poi-data-sourcing.md](../docs/research/11-kakao-naver-poi-data-sourcing.md) — Tier 2 of how Kakao/Naver actually source their own place data: anyone can suggest a correction, but a human reviews it before anything publishes), and curated ferry-schedule/dive-site/border-crossing reference data (added 2026-09-11 per [docs/research/12-ferry-dive-site-data-sourcing.md](../docs/research/12-ferry-dive-site-data-sourcing.md) — extensive research found no API/feed/database exists anywhere for any of the three, government or otherwise, so this project maintains its own). None is blocked by any Belize-specific data problem the way most of this project's remaining feature gaps are — all of it is pure product engineering on top of infrastructure that already exists.

## Model: a short code, not a user account

No login, no friend graph — a share is just a random 6-character code (`create_share` → `{code, expiresAt}`). Give the code to whoever should see your position; they enter it to watch. This is the same trust model as a shared document link, **not** real authentication — good enough for a hobby-scale v1, called out explicitly here (and in `app/main.py`'s own header comment) so it's never mistaken for more secure than it is.

**Sliding expiry, not fixed**: every position update (`PUT /shares/{code}`) pushes `expires_at` forward by 6 hours again. An actively-shared location effectively never expires while genuinely in use — but a share nobody's updating anymore (app closed, forgot to tap "stop") ages out on its own rather than a leaked code staying valid forever. `GET`/`PUT` both treat an expired row as "not found"; something still has to actually `DELETE` old rows eventually — see `scripts/cleanup_expired_shares.sh`.

**Shared lists have no expiry at all**, deliberately — unlike a live location, a saved list of places isn't inherently ephemeral, and Naver's own version doesn't expire shared lists either. They persist until their owner explicitly deletes them (`DELETE /lists/{code}`).

**Hazard reports use a different secret entirely**: not a short human-readable code (nobody needs to read a hazard report's ID out loud), but a longer `deleteToken` bearer secret returned only to the reporter, kept on-device, needed to retract the report early. Anyone (not just the reporter) can "confirm" a report is still valid — that's the whole point, it's a shared signal. Each hazard type gets its own default lifetime (a checkpoint moves on faster than a real flood does), and every confirmation slides that expiry forward again, capped at 3 days from the original report — same idea as location shares' sliding TTL, just driven by the community instead of the original reporter's own activity.

**POI corrections have no per-submitter secret at all** — unlike everything else in this service, nobody needs to retract or manage their own submission afterward, and there's no per-user identity here to gate on anyway (submissions are anonymous). What's different is the *moderation* model: a correction starts `pending` and stays that way until a human explicitly approves or rejects it via a **local admin script**, never an HTTP endpoint (see the API table below and `scripts/review_poi_corrections.py`'s own header comment for why that's a deliberate choice, not an oversight).

**Ferry routes, dive sites, and border crossings aren't Postgres rows at all** — they're hand-maintained JSON files (`sharing/data/ferry_routes.json`, `sharing/data/dive_sites.json`, `sharing/data/border_crossings.json`), read fresh off disk on every request. Neither dataset is crowd-submitted or mutable through this API (both are GET-only); they change on a months-long cadence by someone directly editing the file and re-checking sources, not through any UI or database write — a relational schema would be pure overhead for content that's essentially a maintained document, not user-generated data. Editing a file and running `docker compose restart sharing` (no rebuild) picks up the change immediately.

## Why a custom service, not an off-the-shelf tool

Every other backend piece in this project is a proven, self-hosted OSS tool (Nominatim, Typesense, Valhalla, Martin) — deliberately, per this project's own established pattern of reaching for a real tool before writing custom code. This one's different on purpose: the actual logic here (four small endpoints over one Postgres table) is genuinely too small to justify standing up unfamiliar new infrastructure just to keep that pattern intact — e.g. Redis + a Redis-to-HTTP bridge (`webdis`) would be two brand-new pieces of infrastructure this project has never touched, in service of a feature this size. A small [FastAPI](https://fastapi.tiangolo.com/) app (MIT-licensed, consistent with Locked Decision 4) reusing the **same** `belize` Postgres database every other service already writes to was the simpler choice in practice, not just in principle.

## User profiles (added 2026-09-15) — the one thing here that *is* a real account

Everything above shares one deliberate trait: **no accounts, no real authentication** — a random code or bearer secret is the entire access model. Profiles are the exception, and the first feature in this app needing real identity. See [docs/research/14-naver-kakao-profile-systems.md](../docs/research/14-naver-kakao-profile-systems.md) for the research this is built from; the short version: not a Naver/Kakao-style account system either way — this app is iOS-only, so the deciding factor for *how* is Apple's own App Store rules, not either Korean platform's approach.

**Two sign-in methods, both optional per profile row** (a profile is keyed by its own internal `id`, not by either method directly, specifically so it can have one, the other, or — later — both without a schema change):

- **Sign in with Apple**, built first. A profile is keyed by Apple's own stable per-app user identifier (the identity token's `sub` claim) — this service never sees or stores a real Apple ID or email. Flow: the mobile app runs Apple's native Sign in with Apple UI, gets back a signed **identity token**; `POST /auth/apple` (`{identityToken}`) verifies it against Apple's own published public keys (fetched live from `https://appleid.apple.com/auth/keys`, cached in-process for 24h) and checks `iss`/`aud`/`exp`/signature; first-ever sign-in for a given Apple user id *is* account creation, no separate signup step. **Turned out to have a real prerequisite found only once it mattered**: Sign in with Apple requires the **paid Apple Developer Program membership ($99/year)** — a free "Personal Team" account can't enable the capability at all, in Xcode or the Developer Portal, confirmed via live research before assuming it. The code is fully built and working (see mobile/README.md's Profile section for exactly how far it was verified) — it's just not usable on a free account, which is why the next method exists.
- **Email + password**, added the same day once the above turned out to be a real blocker. This app's own first-party account system — not a third-party login, so it **doesn't trigger App Store Review Guideline 4.8's "must also offer Sign in with Apple" rule at all** (that rule only ever applies to third-party/social logins — Google, Facebook, etc. — never to an app's own email/password system, confirmed explicitly since it's the one thing that would have made building this pointless). `POST /auth/signup` (`{email, password}`) hashes the password with `bcrypt` and stores the email lowercased; `POST /auth/login` checks it back. The exact same generic `401 "Incorrect email or password"` covers both a wrong password and a nonexistent email — confirmed deliberately, not incidentally, so a login attempt can't be used to enumerate registered addresses one guess at a time. No password-reset flow yet — see the email-verification section right below for the piece it's still missing (a resend/reset always needs somewhere to send it).

### Email verification (added 2026-09-15, same day)

A 6-digit code, not a clickable link — this service has no hosted web page for a link to land on and this app has no deep-linking set up, so a code read from the inbox and typed back into the app is the simpler fit, not just the more common one. `POST /auth/signup` generates one (`issue_verification_code`), stores it in a new `email_verification_codes` table (one row per profile — a resend overwrites the pending code rather than creating a second live one), and sends it via [Resend](https://resend.com) — chosen after checking current free-tier options: 3,000 emails/month, permanently free, a plain HTTP API needing no new Python dependency (`requests`, already added for Apple's JWKS fetch, covers it).

**Real caveat, confirmed before assuming otherwise**: without verifying your own domain with Resend, its shared `onboarding@resend.dev` sender can only deliver to the email address the Resend account itself signed up with — not to arbitrary real users. Fine for this project's current dev/testing scope; real delivery to real users needs that domain-verification step later, in your own Resend account. Until `RESEND_API_KEY` is set at all, `send_verification_email` **prints the code to this service's own log** instead of emailing it (`docker logs belize-sharing`) — the entire feature is fully testable with zero external accounts, real delivery is a drop-in once the key exists.

`POST /auth/verify-email` (`{code}`, auth) checks it against the pending row: a 15-minute expiry (`EMAIL_VERIFICATION_TTL`), a 5-attempt cap per code (`MAX_VERIFY_ATTEMPTS`) independent of the endpoint's own `VERIFY_LIMIT` (5/minute) rate limit — two separate backstops against guessing a 6-digit code, not just one. `POST /auth/resend-verification` (auth) issues a fresh one; a no-op (not an error) if the profile is already verified or has no email at all (an Apple sign-in). Verification is a soft nudge, not a hard gate — an unverified account works normally everywhere else in this API.

**Verified directly against the running service, including a real correctness bug caught by testing rather than assumed away**: a wrong code's attempts-increment has to commit in its own transaction block, separate from the one that raises the resulting 400 — doing both in the same `with conn:` block would silently roll the increment back along with the (correctly-desired) non-write on failure, since raising inside that block rolls back everything in it. Confirmed the fix works: signup's code appearing in the dev-fallback log, a wrong code rejected with the attempt actually persisted afterward, a malformed (non-6-digit) code failing Pydantic validation without touching attempts at all, the correct code flipping `email_verified` and deleting the pending row, an already-verified resend correctly no-op'ing, and a no-email profile correctly refusing to resend. Then live in the Simulator through the real mobile UI: signed up, watched the verification banner appear, entered a wrong code and watched it get rejected and logged, then entered the real code and watched the banner disappear for good.

**Follow-up (2026-09-15, same day) — two defenses ported from a real production reference**: asked to check how a reference system (a separate production project with a mature magic-link/code login system — not part of this repo, reviewed directly from its own source) handles this, before assuming the design above was solid enough as-is. Two concrete gaps turned up, both closed:

1. **Resend now reuses the still-valid code instead of rotating it.** The original version called `issue_verification_code` (mint a fresh code, reset `attempts`) on *every* resend — which meant a resend-then-guess loop could reset the 5-attempt cap as many times as resends were allowed, defeating it entirely. `POST /auth/resend-verification` now checks whether the pending code is still unexpired first: if so, it resends that exact code, under its own separate limits (`send_count`/`MAX_CODE_SENDS` = 5 sends, `last_sent_at`/`CODE_RESEND_COOLDOWN` = 30s between them) that don't touch `attempts` at all. Only a genuinely expired (or missing) code still goes through `issue_verification_code` for a real fresh start.
2. **A second, cumulative attempt budget per email** (`window_started_at`/`window_attempts`, `EMAIL_CODE_ATTEMPT_WINDOW` = 15 minutes, `EMAIL_CODE_ATTEMPT_BUDGET` = 10) — this is what actually closes the hole at the root, since fix #1 alone still lets a fresh code (after a real expiry) reset the per-code counter. This budget is deliberately untouched by `issue_verification_code`, scoped to wall-clock time instead: 10 wrong guesses against *any* code for this email within 15 minutes blocks further code entry — even the correct code — until the window elapses. Checked *before* the per-code cap, with its own distinct message ("wait a while," not "request a new code," since a new code doesn't help here).

**Verified directly against the running service, every path**: the reused-code case (code stays identical across a resend, `send_count` increments), the cooldown (a forced-immediate resend correctly 429s), the send cap (forced to the limit, correctly 400s), a genuine expiry correctly triggering a real fresh code (different value, counters reset), the cumulative budget accumulating correctly across multiple codes (seeded realistic prior state, not fabricated), the exact boundary (a 10th wrong guess still processes normally; the *next* attempt after that — even submitting the actually-correct code — is blocked by the cumulative check specifically, not a coincidental wrong guess), and the window correctly resetting once 15 minutes have genuinely elapsed (the correct code then succeeds). No mobile changes were needed for this round — the client already surfaces whatever message the server sends verbatim, confirmed already correct for this exact display path in the previous round.

Either method ends the same way: an opaque **session token** (a bearer secret, same trust model as every other code/token in this service). Every other `/profile*` endpoint takes it as `Authorization: Bearer <token>` — cheap to check (one Postgres lookup) versus re-verifying a password hash or a JWT against Apple's JWKS on every request. `/auth/signup`, `/auth/login`, and `/auth/apple` all sit behind a tighter `AUTH_LIMIT` (5/minute, vs. the usual 10/minute `MUTATE_LIMIT`) specifically to slow down password-guessing against `/auth/login`.

**Profile customization, v1**: a nickname (default "Explorer ####", editable, 1-24 chars) and a pick from a small fixed set of Belize-themed emoji avatars (🧭🐢🦜🦞🐬🌴🏝️⛵🦋🐆) — enforced server-side, not just in the mobile picker. Deliberately **not** an uploaded photo: the research doc's own conclusion was to start at lightweight identity, not copy Naver/Kakao's years-deep reviewer-grade/badge/creator economy. A real photo avatar (the research doc worked through the `bytea`-vs-Cloudflare-R2 storage tradeoff already) is a clean future addition to the same `profiles` table, not a redesign — not built now because nothing would exercise it yet.

**Account deletion** (`DELETE /profile`) exists because Apple requires it — [App Store Review Guideline 5.1.1(v)](https://developer.apple.com/app-store/review/guidelines/#5.1.1) mandates that any app offering account creation must also let a user delete that account from within the app, not just stop using it. It's a **two-stage soft delete**, not an immediate `DELETE FROM profiles` — see the Follow-up right below for why and how.

**Follow-up (2026-09-15, same day) — soft delete + a 30-day grace period, ported from a real production reference**: asked to check how the reference system handles account deletion too, before finalizing this endpoint. Its real `withdraw()`/`UserPurgeScheduler` do a two-stage soft delete (anonymize + kill sessions immediately, hard-purge 30 days later, that figure explicitly tied to Korea's PIPA) rather than an instant hard delete — and separately, asked to check Belize's own law on this specifically. Belize's Data Protection Act, 2021 (Act No. 45 of 2021) is real and in force, and does have a Right to Erasure ("without undue delay" once data's no longer needed) plus a storage-limitation principle — but **no numeric retention/grace-period figure**, unlike PIPA's clear 30 days. Told to proceed with the same design regardless of that outcome, on its own UX/safety-net merits (a short recovery window against an accidental or coerced deletion) rather than a claim that Belizean law requires it specifically.

What actually changed in `DELETE /profile`, all in one transaction: `apple_user_id`/`email`/`password_hash` are set `NULL` and `deleted_at` is recorded, instead of deleting the row; every session for the profile is deleted outright (no longer relying on `ON DELETE CASCADE`, since the row itself isn't being deleted); any pending `email_verification_codes` row is deleted too. A real, deliberate simplification versus the reference system: no tombstone email value (`"deleted+id@removed..."`) is needed to dodge the `email`/`apple_user_id` `UNIQUE` constraints, because Postgres (unlike a naive unique index) doesn't treat two `NULL`s as equal — nulling the field is already enough to free it for a brand-new signup immediately. `nickname`/`avatar_emoji` are deliberately left alone (unlike the reference system nulling name/phone) since this app never collects a real name anywhere — the nickname was never PII. `profiles_has_an_auth_method`'s `CHECK` constraint gained an `OR deleted_at IS NOT NULL` escape hatch so a soft-deleted, now auth-method-less row doesn't itself violate it. `scripts/purge_deleted_profiles.sh` (new) hard-deletes any row past its 30-day grace period — run occasionally (cron, or by hand), same "housekeeping, not required for correctness" role as `scripts/cleanup_expired_shares.sh`; no reference-style `purged_date`/distributed-lock bookkeeping, since a plain `DELETE` is already idempotent and this project is single-instance. No self-service "undo my deletion" either, matching the reference system's own explicit policy — recovery within the grace window would be a manual admin action, not a missing feature.

**Verified directly against the running service**: signed up, confirmed the row exists with `deleted_at` null; deleted the account, confirmed the session token 401s immediately (`GET /profile` → "Invalid or signed-out session") and the row survives with every auth field `NULL` and `deleted_at` set; signed up again with the *exact same email* and confirmed it succeeds immediately (no `UniqueViolation`) rather than needing to wait out the grace period; ran `scripts/purge_deleted_profiles.sh` right after the soft-delete and confirmed it correctly leaves the row alone (grace period not elapsed); backdated `deleted_at` past 30 days and re-ran the purge, confirming it removes exactly that row and leaves an unrelated live row untouched; ran the purge a second time afterward and confirmed it's a no-op (idempotent). Also caught and fixed a real deployment mistake mid-verification, not just a code bug: `sharing`'s `Dockerfile` `COPY`s `main.py` into the image rather than mounting it, so `docker compose restart` alone (this project's usual "edit and restart" workflow for the *mounted* data/scripts files) silently kept running the old hard-delete code — needed `docker compose up -d --build` instead, same as any other `main.py` change. Full `pytest` suite (23 tests) still passes. No mobile changes needed: `DELETE /profile`'s request/response shape is unchanged, and the existing confirmation copy ("This permanently removes your profile... This can't be undone") stays accurate from the user's own vantage point — there's no self-service undo either way, soft-delete or hard-delete.

**Follow-up (2026-09-15, same day) — a real SQL-injection hole found by a 9-angle code-review pass on the commit above, fixed the same day**: `scripts/purge_deleted_profiles.sh` originally made its grace period configurable via a `GRACE_PERIOD_DAYS` env var, interpolated directly into the SQL string handed to `psql -c` (which, unlike every psycopg2 call in `main.py`, has no parameter binding at all). Three independent review passes converged on the same finding, one tracing a working proof of concept end-to-end: `GRACE_PERIOD_DAYS="0'; DROP TABLE profiles; --"` closes the `INTERVAL` literal early and appends an arbitrary second statement, executing silently (both statements are syntactically valid, so `set -e` never fires). The same unvalidated variable also let a plain typo (`GRACE_PERIOD_DAYS=0` or a negative value) silently defeat the entire 30-day grace period with no error at all. The review separately flagged that this override was never actually used anywhere in the project (grepped: no docker-compose entry, no CI step, no doc ever set it) and was inconsistent with the sibling `cleanup_expired_shares.sh`, which just hardcodes its interval — so the fix for all three findings was the same one-line move: delete the env-var override entirely and hardcode `INTERVAL '30 days'` directly, matching the sibling script. Verified live: the exact injection payload above now runs as a normal no-op with zero effect (the `profiles` table intact, row count unchanged), and the purge script's own no-op/removes-only-the-expired-row/idempotent-on-rerun behavior was re-confirmed unchanged after the fix. The review's other findings (a one-directional gap in the `profiles_has_an_auth_method` CHECK constraint, a missing `updated_at` bump and idempotency guard in `delete_profile`'s UPDATE, a narrow cross-connection race, and zero automated test coverage for the whole profile/auth feature) were reported but **not yet fixed** — left for a future pass.

**Follow-up (2026-09-15, same day) — fixed the `updated_at`/idempotency finding from the same review**: `delete_profile`'s UPDATE now also sets `updated_at = %s` (matching every other write to `profiles` — see `update_profile`) and gained a `WHERE id = %s AND deleted_at IS NULL` guard. Without the guard, two devices racing a near-simultaneous `DELETE /profile` for the same account (both still holding valid sessions the instant either request starts, before either's session-cleanup commits) could each run the UPDATE, with the second one silently overwriting `deleted_at` with a later timestamp and resetting `scripts/purge_deleted_profiles.sh`'s grace-period clock. With the guard, a second write to an already-soft-deleted row is a genuine no-op — still returns `{"ok": true}`, since deleting an already-deleted account is never itself an error, same reasoning as `sign_out`. **Verified**: a normal delete confirmed `updated_at` now bumps exactly alongside `deleted_at` (both later than `created_at`, which stays untouched); since a real second HTTP call can't reach this code path once sessions are killed (the auth dependency 401s first), the guard itself was verified directly at the SQL layer — re-running the identical guarded UPDATE against an already-soft-deleted row with a new timestamp affected 0 rows and left `deleted_at`/`updated_at` completely unchanged. Full `pytest` suite (23 tests) still passes. The CHECK-constraint gap, the cross-connection race, and the missing test coverage remain open.

**Follow-up (2026-09-15, same day) — fixed the remaining three findings from the same review**:

1. **`profiles_has_an_auth_method` is now a genuine two-way invariant.** The original version only checked `deleted_at IS NOT NULL` — it never actually required the auth fields to be `NULL`, so a row with `deleted_at` set but a still-live `email`/`password_hash` would have passed trivially via the other OR-branch. Now: `(deleted_at IS NULL AND has-an-auth-method) OR (deleted_at IS NOT NULL AND apple_user_id/email/password_hash all NULL)` — a profile is either live-with-a-method or fully-anonymized, nothing in between can exist, enforced by Postgres itself rather than trusted to `delete_profile`'s application code. **Verified**: directly inserting a live row then trying to set `deleted_at` on it *without* nulling the auth fields now fails with a real `CheckViolation` (confirmed the exact Postgres error and that the row's original state was untouched by the rejected statement); a genuine soft-delete (everything nulled together) still succeeds exactly as before.
2. **Closed the narrow cross-connection race.** `get_current_profile_id`'s session lookup now `JOIN`s to `profiles` and requires `deleted_at IS NULL` (today provably redundant, since `delete_profile` kills every session in the same transaction that sets `deleted_at` — but it turns "a valid session can never belong to a deleted profile" into something Postgres enforces on every call, not a fact that just happens to hold because nothing else currently violates it). `get_profile`, `update_profile`, and `resend_verification`'s own `profiles` queries all gained `AND deleted_at IS NULL` too, closing the specific gap a reviewer found: a request that legitimately passed the auth check a moment *before* a concurrent `DELETE /profile` commits, whose own separate-connection query then lands a moment *after* — without the filter, that could return a stale 200 (nickname/avatar/etc. are never touched by soft-delete) instead of the clean 404 the old hard-delete design guaranteed in the same race. `update_profile` also gained an explicit 404 for a non-matching row — the old code had no such check and would have crashed (`NoneType` isn't subscriptable) if its `UPDATE ... RETURNING` ever matched zero rows. `verify_email` needed no change: its own query targets `email_verification_codes`, which dies in the exact same atomic transaction as the session, so it was already safe by the same reasoning `get_current_profile_id` now makes explicit.
3. **The whole profile/auth/deletion feature has real automated test coverage for the first time** — `sharing/app/test_main.py` gained `TestAuth`, `TestProfile`, and `TestAccountDeletion` (18 new tests, `TestAccountDeletion` specifically regression-testing every bug this review found and fixed: the `updated_at` bump, the idempotency guard, and the CHECK constraint's two-way enforcement). Two of the new tests reach into the database directly via `get_conn()` — necessary, not just convenient, since a profile's internal id is never exposed in any API response, and the idempotency guard's actual failure mode (two concurrent requests racing at the DB level) can't be reproduced deterministically through the public HTTP API at all; both are verified instead by re-running the exact guarded SQL statement `delete_profile` uses and asserting it's refused. Sign in with Apple remains untested (needs a real Apple-signed identity token, which nothing in this environment can produce).

**Verified**: 41/41 tests pass (23 original + 18 new), confirmed stable across two consecutive full runs; the shared dev database ends each run holding only anonymized (`email IS NULL`) rows, never a live leftover — confirmed via `count(*) vs count(email)`. Also caught and fixed a real, unrelated process gap mid-pass: editing `test_main.py` on the host left the running container's bind-mounted view of the file pointing at a now-unlinked inode (`cat`/`pytest` reported "No such file or directory" even though `ls` still showed stale cached metadata) — a plain `docker compose restart` (no rebuild; the file is mounted, not baked into the image) was enough to pick up the fresh file, same as this project's existing "edit a mounted file, restart, no rebuild needed" pattern for `data/`/`scripts/`.

**Follow-up (2026-09-16) — a real Privacy Policy + Terms of Service, presented and required at signup**: the first item from [docs/research/15-belize-legal-compliance-audit.md](../docs/research/15-belize-legal-compliance-audit.md)'s own action list — it closes three separate gaps at once (Apple's hard App Store requirement for a reachable privacy policy; the Electronic Transactions Act's own logic, which needs an actual agreement to exist before its e-signature-validity protection does anything, and this app's signup flow showed no terms at all before this; and most of the Data Protection Act's transparency duty). Both documents are plain hand-written HTML (`sharing/data/privacy_policy.html`/`terms_of_service.html` — same "curated file, re-read fresh on every request, no rebuild needed" pattern as the ferry/dive-site JSON content, via a new `read_html_data` helper), served unauthenticated by two new endpoints so an App Store reviewer or anyone else can open them with no account. `profiles` gained `terms_accepted_at`/`terms_version` columns (both `NOT NULL`, never touched by `delete_profile`'s soft-delete — a historical consent record, not an auth credential); `SignupBody` gained a required `termsAccepted` field, rejected with a clear 422 message unless it's `true`.

`AppleSignInBody` needed real care, not just the same validator copy-pasted: unlike `/auth/signup`, which always creates a brand-new account, `/auth/apple`'s same request body also serves a *returning* user's routine sign-in — and Pydantic validates the body before `sign_in_with_apple` ever runs, before it's known which case this is. An unconditional check would have wrongly rejected a returning user's sign-in for not re-checking a box they already checked once. Fixed by not validating `terms_accepted` at the Pydantic-body level at all for this one; instead `sign_in_with_apple` checks it manually, only inside the branch that actually creates a new profile — caught this exact bug in my own first draft before it ever ran (a returning Apple sign-in would have 422'd), by re-reading the "only meaningful the first time" comment I'd already written and realizing the code didn't actually match it yet.

Mobile: `ProfilePanel`'s signup form gained a real checkbox ("I agree to the **Terms of Service** and **Privacy Policy**," both tappable, each opening the live HTML via `Linking.openURL` — see `src/legal/api.ts`) that gates the "Create account" button exactly like the email/password fields already did; login mode doesn't show it at all (nothing to re-confirm). ## API

| Endpoint | Purpose |
|---|---|
| `POST /shares` — body `{lat, lon, label?}` | Start sharing a location. Returns `{code, expiresAt}`. |
| `PUT /shares/{code}` — body `{lat, lon}` | Push a new position. Also refreshes `expires_at`. 404 if the code doesn't exist or already expired. |
| `GET /shares/{code}` | Read the current position. Returns `{lat, lon, label, updatedAt, expiresAt}`. 404 if not found/expired — the viewer side polls this. |
| `DELETE /shares/{code}` | Stop sharing immediately (the explicit "I'm done" action, not just waiting for expiry). |
| `POST /lists` — body `{label, places}` | Create a shared list. Returns `{code}`. No expiry. |
| `PUT /lists/{code}` — body `{label, places}` | Re-sync the list's contents (the owner's device calls this whenever it changes locally — a viewer polling `GET` then sees the update). 404 if the code doesn't exist. |
| `GET /lists/{code}` | Read a shared list. Returns `{label, places, updatedAt}`. 404 if not found — the viewer side calls this. |
| `DELETE /lists/{code}` | Delete the list entirely. |
| `POST /hazards` — body `{type, lat, lon, note?}` | Report a hazard. Returns `{id, deleteToken, expiresAt}` — TTL depends on `type` (see `HAZARD_TYPE_TTL` in `app/main.py`). |
| `GET /hazards?min_lat=&max_lat=&min_lon=&max_lon=` | List non-expired reports in a bbox. Returns `{hazards: [...]}`. |
| `POST /hazards/{id}/confirm` | "Still here" — bumps `expires_at` forward (capped at 3 days from the original report) and increments `confirm_count`. |
| `DELETE /hazards/{id}?delete_token=` | Retract a report. 404 if the token doesn't match (or the report doesn't exist). |
| `POST /hazards/{id}/report` — body `{reason}` | Flags a report for a human to review (`reason` is one of `not_here`\|`spam`\|`duplicate`\|`inappropriate`) — never auto-hides anything, see `scripts/review_hazard_reports.py`. Anyone can report, no `delete_token` needed. 404 if the report doesn't exist or has expired. |
| `POST /poi-corrections` — body `{poi_id, poi_name, field, current_value?, suggested_value?, note?}` | Submit a correction (`field` is `name`\|`category`\|`closed`\|`other`). Returns `{id}`. Always lands as `pending` — never applied here. |
| `GET /poi-corrections?status=pending` | List corrections by status. Read-only — safe to leave open without auth, since nothing here can be mutated through this endpoint. |
| `GET /ferry-routes` | Returns the curated water-taxi/ferry route list — read straight from `data/ferry_routes.json`, not a database. |
| `GET /dive-sites` | Returns the curated dive-site list — read straight from `data/dive_sites.json`, not a database. |
| `GET /border-crossings` | Returns the curated border-crossing info (hours/fees/documents/scam warnings) — read straight from `data/border_crossings.json`, not a database. |
| `POST /auth/signup` — body `{email, password, termsAccepted}` | Creates a new email/password profile. `termsAccepted` must be `true` (422 otherwise — see the Terms of Service/Privacy Policy follow-up below). Returns `{sessionToken, profile}`. 409 if that email is already registered, 422 for an invalid email or a too-short password. |
| `POST /auth/login` — body `{email, password}` | Signs in with email/password. Returns `{sessionToken, profile}`. 401 (identical wording for both cases, to avoid email enumeration) for a wrong password or a nonexistent email. |
| `POST /auth/apple` — body `{identityToken, termsAccepted}` | Verifies an Apple Sign in with Apple identity token; creates a profile on first sign-in (`termsAccepted` only actually enforced on that first-ever sign-in — see the follow-up below for why a returning user isn't blocked by it). Returns `{sessionToken, profile}`. 401 if the token doesn't check out. |
| `DELETE /auth/session` | Signs out this device only (deletes the session token in the `Authorization: Bearer` header). Always `{ok: true}`, even with no/an invalid token — signing out is never itself an error. |
| `GET /profile` (auth) | Returns `{nickname, avatarEmoji, memberSince}` for the signed-in profile. |
| `PUT /profile` (auth) — body `{nickname?, avatarEmoji?}` | Updates the nickname (trimmed, 1-24 chars) and/or avatar (must be one of the fixed emoji choices — see main.py's `AVATAR_EMOJI_CHOICES`). 400 if neither is given or the avatar isn't a valid choice. |
| `DELETE /profile` (auth) | Soft-deletes the account — required by App Store Guideline 5.1.1(v). Nulls every auth field, kills every session for this profile immediately; `scripts/purge_deleted_profiles.sh` hard-deletes the row 30 days later. |
| `POST /auth/verify-email` (auth) — body `{code}` | Checks the 6-digit code against the pending one for this profile. Sets `emailVerified` on success. 400 for a wrong/expired code or too many attempts, 422 if not exactly 6 digits. |
| `POST /auth/resend-verification` (auth) | Issues and sends a fresh code. `{ok: true}` no-op if already verified or the profile has no email at all. |
| `GET /privacy-policy` | Returns the Privacy Policy as HTML — read straight from `data/privacy_policy.html`. Unauthenticated, so an App Store reviewer (or anyone) can open it with no account. |
| `GET /terms-of-service` | Returns the Terms of Service as HTML — read straight from `data/terms_of_service.html`. Unauthenticated, same reasoning as above. |
| `GET /health` | `{ok: true}` |
| `GET /admin` | The moderation page (HTML/JS, no secrets baked in) — see "Moderation page" below. |
| `GET /admin/hazard-reports` (admin token) | Every flagged, non-expired hazard report, worst-first. |
| `POST /admin/hazard-reports/{id}/dismiss` (admin token) | Clears the flag(s) on a report; it stays live. |
| `DELETE /admin/hazard-reports/{id}` (admin token) | Hard-deletes a hazard report. |
| `POST /admin/poi-corrections/{id}/approve` (admin token) | Approves a correction — auto-patches Typesense for `name`/`category`, otherwise marks reviewed and returns a `manualAction` string. |
| `POST /admin/poi-corrections/{id}/reject` (admin token) | Rejects a pending correction. |

## Hardening (2026-09-11)

Picked as the next priority after a full engineering audit flagged this as the service most worth hardening before any real users touch it — it's the one thing in this project handling live GPS data and public writes with no auth at all. Four changes, all in `app/main.py` unless noted:

- **Cryptographically random codes/tokens**: `generate_code()` and `generate_delete_token()` used `random.choices()` — Python's Mersenne Twister, a fine PRNG for simulations but not a cryptographic one, and predictable if its internal state is ever recovered. Both now use `secrets.choice()` (the `secrets` module wraps the OS's own CSPRNG) instead — same alphabet, same length, no behavior change, just a real security property where there wasn't one. This matters here specifically because a share code or delete token *is* the entire access model — there's no account behind it to fall back on.
- **Rate limiting** via [slowapi](https://github.com/laurentS/slowapi) (MIT, in-memory counters — no Redis needed at this scale, one process), keyed by client IP, on every endpoint. Not one blanket number: `MUTATE_LIMIT` (10/minute) for creating/deleting a share, list, hazard report, or correction; `POLL_LIMIT` (30/minute) for the reads/updates that happen every few seconds during genuinely active use (an in-progress location share, a viewer watching one); `STATIC_LIMIT` (20/minute) for the curated ferry/dive-site/border-crossing content. `/health` is deliberately exempt — a health check should never be the thing that starts failing under load.
  - **`POLL_LIMIT` is shared across every feature polling from the same device, not per-code** — found later (2026-09-15), when the mobile app's Meet Up live-location-sharing fusion (see `mobile/README.md`) started polling `GET /shares/{code}` for up to 5 participants at once: at a 10s interval, 5 codes alone is 5 × 6 = 30 requests/minute, the *entire* budget for that client IP, with no headroom left for anything else (this same service's own "view a share" feature, polled from the same device). Confirmed by directly bursting 31 requests against a real share — the 31st gets a real 429. The fix landed client-side (a wider poll interval, plus correctly treating a 429 as "try again next tick," not "the share is gone") rather than raising this limit — see `mobile/README.md`'s own follow-up note for why.
- **Input validation** that was previously minimal: every lat/lon field across every request body and query string now has real `ge`/`le` range constraints (`-90..90`, `-180..180`) instead of accepting any float; `GET /hazards`'s bbox additionally rejects `min > max` and caps the span at 10° per side (Belize's own bounds are roughly 1° × 1.5° — this is generous room to zoom out, not a functional limit, while still refusing an unbounded/planet-scale range scan); every previously-unconstrained free-text field (list place names, correction fields, hazard notes) now has a `max_length`; a POI correction's `field` and a hazards-queue `status` filter are now `Literal` types matching the mobile client's own TypeScript union exactly, rejecting anything else, rather than silently accepting garbage a client should never have sent.
- **Docker ports bound to loopback only**: every `docker-compose.yml` in this project (`backend/`, `sharing/`, `geocoding/`, `search/`, `routing/`) now publishes its ports as `127.0.0.1:<port>:<port>` instead of just `<port>:<port>` (which Docker defaults to all interfaces). The Simulator/host already reach every service over `127.0.0.1` — this was true before and needed no client-side change — so this only removes exposure to the local network, with zero functional difference. Confirmed via `docker ps`: every belize-* container now shows `127.0.0.1:PORT->PORT/tcp`, not `0.0.0.0:PORT->PORT/tcp`.

**Deliberately not changed today**: the `devpass123` dev password's actual value. It's a local-only Postgres instance never exposed to a real network (doubly so now that every port above is loopback-only) — rotating the literal string right now provides no real security benefit and would just require touching several files for nothing. What *did* change: every credential across `backend/`, `sharing/`, `search/`, and `geocoding/`'s `docker-compose.yml` files was a hardcoded literal with no way to override it short of editing the compose file directly — now each reads `${VAR:-dev-default}`, and a `.env.example` in each of those four directories documents exactly what to set. Copy one to `.env` (already `.gitignore`d) and docker compose picks it up automatically; leave it alone and dev keeps working with zero setup. Tested this actually works, not just that the syntax looks right — `docker compose config` with a throwaway `.env` present showed the override taking effect, and reverted correctly once removed. One coupling to know about: `sharing/.env`'s `DB_PASSWORD` must match `backend/.env`'s `POSTGRES_PASSWORD` exactly, since `sharing` connects to that same shared Postgres instance over the Docker network — both `.env.example` files say so.

**Verified**: rebuilt and restarted the service, then tested directly against the running container (not just code review) — a valid `/shares` create still works; an out-of-range lat is rejected with a clear 422; an oversized `/hazards` bbox and a `min > max` bbox are both rejected with clear 400s; an invalid `poi-corrections` status and an invalid correction `field` are both rejected; 12 rapid `POST /shares` calls succeed 10 times then get a 429 for the rest, confirming the 10/minute limit actually engages; a full report → confirm → delete hazard cycle still works end-to-end with the new `secrets`-based 24-character token, and a wrong-length token is rejected before ever reaching the database. Confirmed all 6 backend containers came back on loopback-only ports via `docker ps` and still answer real requests over `127.0.0.1`. Relaunched the mobile app itself afterward and confirmed the map, search, and every backend-dependent feature still work with no regression. Test data created during this pass was cleaned up afterward.

## Moderation page (2026-09-16)

`scripts/review_poi_corrections.py` and `scripts/review_hazard_reports.py` were CLI-only from the start, deliberately — see their own header comments. Researched how a much larger internal reference product (an unrelated company's AI chat platform, used purely as an architecture comparison, not affiliated with this project) builds its own admin console before building this: separate small surface, auth enforced server-side rather than trusted from the UI, and a config/content store the running service reads live rather than one baked into a deploy. The right-sized version of that here isn't a new app — it's a static page this same service already serves, gated by one new dependency.

**`ADMIN_TOKEN`** (`sharing/.env`, see `.env.example`) gates every mutating `/admin/*` route via `require_admin` — a single long random secret compared in constant time (`secrets.compare_digest`), not the profile/bcrypt system used elsewhere in this file (there's no "admin profile" concept in this schema, and building one for a single operator would be more auth system than a one-person tool needs). Unset by default, so these routes fail closed rather than open — consistent with this service's own "wide-open CORS/no auth, called out explicitly" posture for everything else: a mutation was never going to be safe to leave open the way a plain read already is.

`GET /admin` serves `data/admin.html` — plain HTML/JS, no build step, no secrets baked in (the token is entered into the page at runtime and sent as an `X-Admin-Token` header on every admin call; stored in `sessionStorage`, so it clears when the tab closes). It lists the same two queues the CLI scripts do — flagged hazard reports and pending POI corrections — with Approve/Reject/Dismiss/Remove buttons calling the new endpoints. The listing itself (`GET /poi-corrections`) stays the existing public, unauthenticated route (nothing there can be mutated); only the actions that change data require the token. Both CLI scripts still work completely unmodified — this is an additional way to do the same moderation, not a replacement.

**A real bug this surfaced, not a hypothetical one**: the first version used `window.confirm()`/`window.alert()` for the destructive actions (reject, remove) and the Typesense-manual-action notice. Testing it live in this session's own Browser tool, its dialog policy silently suppresses native `confirm()`/`alert()` — `confirm()` just returns `false` with a console warning, no dialog ever shown — which would have made Reject/Remove appear to do nothing, and the manual-Typesense-delete instructions never appear at all. This is the exact failure mode the reference-system research (the same comparison referenced above) had already turned up independently: their admin console's own delete-confirmation modal has a comment noting `window.confirm()` was found to no-op under some browser security policies, so they built a custom modal instead. Fixed here the same way: a two-click inline confirm (`armConfirm` in `admin.html` — first click relabels the button and arms it for 3 seconds, a second click within that window actually runs the action) replaces `confirm()`, and a dismissible inline banner replaces `alert()` for the manual-Typesense-delete message.

**Verified**: rebuilt/restarted the container, ran the full suite (58 passed, up from 49 — 9 new tests covering `require_admin`'s token check, the fail-closed-when-unset case, all four new mutation routes, and the auto-applied-vs-manual approve branches).
